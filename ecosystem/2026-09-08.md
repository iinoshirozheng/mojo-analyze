## Repository discoveries and meaningful activity

### R01. Gonzales — path tracing, BVH, GPU wavefront rendering

Repository: https://github.com/gonsolo/Gonzales  
Recent commit: https://github.com/gonsolo/Gonzales/commit/e0bd622f1caba0a2dafce05902d16a525f1d3cee

The Sep-7 commit documents a homogeneous-medium estimator failure found against analytic reference scenes, then checks the fix against analytic cases and pbrt. The project exercises BVH traversal, irregular memory access, stochastic algorithms and GPU rendering rather than another parser/network workload.

**Why interesting:** rendered images are insufficient correctness evidence; stochastic workloads need analytic/reference criteria.  
**Possible experiment:** isolate deterministic ray–box or BVH traversal before attempting whole-renderer timing.

### R02. Decimo — arbitrary precision, carry chains, Python extension boundary

Repository: https://github.com/forfudan/decimo  
Recent commit: https://github.com/forfudan/decimo/commit/1f9696ee0b88172fc0e7804a5c35fa35cce21dd3

A Sep-4 UTC commit reports removing an allocating negated temporary in subtraction and interleaving BigInt carry chains. The author explicitly notes that faster addition did not automatically make multiplication/division faster.

**Why interesting:** dependency-chain latency and allocation can be isolated, while Python-extension overhead must be measured separately from native Mojo.  
**Possible experiment:** equal-width limb addition across sizes with an independent big-integer oracle.

### R03. EmberJson — typed lazy deserialization

Repository: https://github.com/bgreni/EmberJson

The documented API mixes eager fields with lazy wrappers that retain validated source spans and materialize only when accessed.

**Why interesting:** it asks a different performance question from SIMD parsing: how much work can be avoided when an application only needs selected fields?  
**Possible experiment:** selective extraction and full materialization must be benchmarked as distinct work contracts.

### R04. mojo-audio — FFT, mel spectrogram, resampling, VAD and pitch

Repository: https://github.com/itsdevcoffee/mojo-audio

The project separates Mojo DSP from Python/MAX inference and exposes a C-compatible shared-library boundary.

**Why interesting:** audio brings numerical accuracy, streaming latency and regular DSP kernels into the ecosystem radar.  
**Possible experiment:** one FFT or mel-filterbank stage with matched dtype, normalization, windowing and tolerance.

### R05. mojo-raylib — generated raylib bindings for interactive graphics

Repository: https://github.com/kivicode/mojo-raylib

The project generates bindings plus a C shim and explicitly distinguishes generated API coverage from manual runtime testing.

**Why interesting:** a practical route to 2D/3D applications and games without first writing a renderer.  
**Possible experiment:** batched versus individual FFI calls after validating representative struct layouts and resource lifetime behavior.

### R06. MAV — FFmpeg interoperability

Repository: https://github.com/josiahls/mav

MAV is a low-level Mojo binding layer for FFmpeg with image/video encode/decode examples and native-link requirements.

**Why interesting:** frame ownership, format conversion and buffer copies can dominate an interoperability pipeline.  
**Possible experiment:** separate codec time, conversion time and wrapper/copy overhead; do not describe FFmpeg work as pure-Mojo codec performance.

### R07. mojo_libclang — C/C++ AST tooling and binding generation

Repository: https://github.com/MoSafi2/mojo_libclang

The library provides a clang.cindex-like Mojo interface to libclang and couples binding regeneration with layout tests and a C shim.

**Why interesting:** source tooling and ABI verification are an underserved Mojo domain.  
**Possible experiment:** fixed AST traversal with one pinned libclang build, splitting native parser time from wrapper traversal.

### R08. ish — alignment-driven record filtering

Repository: https://github.com/BioRadOpenSource/ish

The CLI/library uses local or semi-global alignment scores, configurable scoring and FASTX/line inputs.

**Why interesting:** dynamic programming and data-dependent computation broaden the current parser/hash-heavy benchmark set.  
**Possible experiment:** isolate a scoring kernel with fixed gap/scoring rules and an independent reference implementation.

### R09. Strata — dense/sparse ML and preprocessing

Repository: https://github.com/ethqnol/Strata

Strata documents estimators, sparse/dense containers, pipelines and serialization. Some numerical operations use LAPACK/BLAS.

**Why interesting:** comparisons must disclose when native BLAS/LAPACK, rather than Mojo loops, do the heavy work.  
**Possible experiment:** one sparse/preprocessing operation with fixed dtype/layout/thread count.

### R10. Kelvin — compile-time dimensional analysis

Repository: https://github.com/bgreni/Kelvin

Kelvin represents quantities and dimensions with compile-time type parameters and unit ratios.

**Why interesting:** it is a correctness-oriented use of Mojo’s type system, not a throughput demo.  
**Possible experiment:** compare typed and scalar expressions for value correctness, assembly shape, code size and compilation cost.

### R11. mtest — supervised test outcomes

Repository: https://github.com/mikeleppane/mtest

The runner distinguishes assertion failures, compile failures, crashes, timeouts and flaky outcomes instead of hiding a failed first attempt behind a later retry.

**Why interesting:** compiler-nightly research needs truthful failure classification before timing evidence is trusted.  
**Possible experiment:** a small fixture corpus with known pass/fail/crash/timeout outcomes.

### R12. mojo-js — browser-facing language prototype

Repository: https://github.com/exergy-connect/mojo-js

The proof of concept parses a supported Mojo subset, emits JavaScript and executes it with a small runtime.

**Why interesting:** mixed-language searches uncover Mojo-targeting tools that a `language:Mojo` search misses.  
**Limitation:** this is not the official compiler, full Mojo compatibility, or an official WebAssembly backend.

### R13. BlazeSeq — high-throughput FASTQ parsing and GPU-oriented batches

Repository: https://github.com/MoSafi2/BlazeSeq

BlazeSeq documents SIMD scanning, zero-copy `FastqView`, owned records, structure-of-arrays GPU batches, compile-time validation switches, FASTA/FAI support and an optional GPU Needleman–Wunsch example. It also documents current limits such as four-line FASTQ records and no paired-end support.

**Why interesting:** bioinformatics provides parsing plus lifetime/ownership and CPU→GPU handoff questions in one real workload.  
**Possible experiment:** same FASTQ corpus across view/owned/batch modes, reporting parsing and copying separately and verifying identical record/base counts plus validation behavior.

### R14. Larecs — archetype ECS in Mojo

Repository: https://github.com/larecs/larecs

Larecs is a performance-oriented archetype ECS with compile-time component checks, a `vectorize`-style SIMD path, resources/scheduling support and optional Tracy profiling. Its README also calls out an important current limitation: only trivial component types are safe; heap-owning component types can leak or trigger undefined behavior.

**Why interesting:** this is directly relevant to Mojo game-engine architecture and exposes archetype transitions, SoA-style iteration and scheduler costs.  
**Possible experiment:** component iteration over a fixed Position/Velocity archetype versus a simple packed-array baseline, with identical update checksums.

### R15. Linamo v0.1.0 — specialized 2D linear algebra

Repository: https://github.com/mojomath/linamo  
Community release discussion: https://forum.modular.com/t/linamo-v0-1-0-linear-algebra-for-mojo-and-decimo-v0-14-0-now-a-python-package-too/3466

Linamo targets Mojo 1.0.0 and specializes in two-dimensional matrix workflows rather than a general ndarray. The README distinguishes `Matrix`, non-owning `MatrixView` and compile-time-shaped `StaticMatrix`, supports scalar and Decimo exact element types, and explicitly chooses `List` storage to favor safe Mojo over raw pointer storage where possible.

**Why interesting:** it provides a new safe-vs-specialized linear-algebra design point and a concrete contrast with NuMojo’s general N-D model.  
**Possible experiment:** a small fixed matrix kernel comparing dynamic Matrix, StaticMatrix and a plain scalar loop, including codegen and bounds/storage effects.

### R16. mojolearn 0.5.0 — cross-vendor GPU classical ML with explicit numerical profiles

Repository: https://github.com/mojolearn/mojolearn  
Package/release metadata: https://pypi.org/project/mojolearn/

PyPI shows version **0.5.0 released Sep 5, 2026**, with a provenance link to source commit `529ec5ec73c81c14826135fe615fac1a7631bf54`. The project separates `fast`, deterministic and certified cross-vendor `identical` numerical profiles, and explicitly states where wheel support, source-build support and certification coverage differ.

**Why interesting:** the strongest idea is not the author benchmark headline but the evidence model: source, binding, built artifact and installed wheel are separate validation classes; numerical identity is scoped to a frozen profile.  
**Possible experiment:** reproduce one small estimator/kernel across supported devices only when hardware is available, preserving profile/version and independent metric checks instead of importing the project’s performance table.

## Original articles, papers and technical reading — 10 selections

### A01. Structured Mojo Kernels
https://www.modular.com/structured-mojo-kernels

March–April 2026 series on TileIO, TilePipeline and TileOp. Useful for studying separation of data movement, scheduling and arithmetic. Treat abstraction cost as a measurable hypothesis.

### A02. Matrix Multiplication on Blackwell
https://www.modular.com/matrix-multiplication-on-blackwell

Historical optimization series for hardware-specific matrix multiplication. Useful as an “optimization ladder”: change one mechanism per step and retain hardware/toolchain provenance.

### A03. Mojo Miji
https://mojo-lang.com/miji/intro

A maintained guide by Yuhao Zhu covering ownership/origins, SIMD, generics and applications. Its August-2026 revision makes it useful learning material, but examples should still be version-pinned before becoming tests.

### A04. When “Magic” Becomes Explicit: Mojo's Take on Metaprogramming
https://mzaks.medium.com/when-magic-becomes-explicit-mojos-take-on-metaprogramming-61bcfafc5145

Maxim Zaks, Feb 6, 2026. A useful design discussion for derived behavior and compile-time reflection; distinguish currently verified syntax from future-looking ideas.

### A05. From OpenCL towards Mojo GPU kernels in digital photo editing
https://forum.modular.com/t/from-opencl-towards-mojo-gpu-kernels-in-digital-photo-editing-first-look/2764

Max Chistokletov, Feb 24, 2026. A non-AI GPU case study based on a Darktable sigmoid kernel. Replication needs an image-wide numerical error contract, not a few visual samples.

### A06. Bringing Blazing Fast State Space Models to the Modular MAX Framework
https://qwerky.ai/blog/bringing-blazing-fast-state-space-models-to-the-modular-max-framework

An implementation narrative covering selective scan, causal convolution and recurrent-state caching. Useful for separating recurrent-model state reuse from transformer-oriented execution assumptions.

### A07. Mojo: MLIR-Based Performance-Portable HPC Science Kernels on GPUs for the Python Ecosystem
https://arxiv.org/abs/2509.21039

Sep 25, 2025 paper covering a stencil, BabelStream, miniBUDE and Hartree–Fock on NVIDIA/AMD hardware. Good historical replication material, but old-toolchain performance must not be copied into a Mojo 1.x scoreboard.

### A08. MojoFrame: Dataframe Library in Mojo Language
https://arxiv.org/abs/2505.04080

May 7, 2025 paper covering filtering, joins, group-by and UDF-style work. A controlled join with explicit cardinality/skew would broaden `mojo-analyze` beyond CSV parsing throughput.

### A09. MojoR — a “Numba” for R
https://forum.modular.com/t/mojor-a-numba-for-r/2718

Feb 2026 author discussion describing an R→Mojo JIT/transpilation prototype and `.Call` ABI integration. No public repository was established from the inspected discussion, so none is invented here.

### A10. Better Stack’s Mojo 1.0 overview
https://betterstack.com/community/guides/ai/mojo/

Updated **Sep 7, 2026**. This is a third-party overview, useful as a current onboarding/readability source rather than an authority for compiler history or corporate facts. Release/compiler claims should be checked against Modular and GitHub before reuse.

## Research candidates

1. **Shared-runner estimator sensitivity** — use existing checksum-valid GitHub Actions artifacts from multiple independent runs to compare mean, median and best-of-N rankings, and quantify whether high-dispersion runs can change conclusions.
2. **Decimo carry-chain isolation** — standalone limb addition with exact correctness oracle and native-vs-extension separation.
3. **BlazeSeq ownership-mode decomposition** — zero-copy views versus owned records/batches with equal validation contracts.
4. **Larecs archetype iteration** — packed component iteration with a simple array baseline and deterministic update checksum.
5. **Linamo static/dynamic matrix codegen** — Matrix versus StaticMatrix versus scalar loop on a small kernel.
