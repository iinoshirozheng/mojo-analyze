## A. Repository discoveries — 12 projects

### R01. Gonzales — physically based rendering, not another HTTP benchmark

**Repository:** https://github.com/gonsolo/Gonzales

**Recent activity:** September 7, 2026 UTC. Commit: https://github.com/gonsolo/Gonzales/commit/e0bd622f1caba0a2dafce05902d16a525f1d3cee

The README describes a Mojo path tracer with BVH construction/traversal, GPU wavefront rendering, sampling, and denoising. Its latest inspected commit message reports a homogeneous-medium estimator defect found against analytic reference scenes, including inconsistent free-flight weighting and missing next-event estimation. This is an author-reported fix, not independently reproduced here.

**Why read it:** it exposes geometry, irregular memory access, stochastic correctness, and CPU/GPU architecture beyond AI inference. A rendered picture alone is not a numerical validation.

**Research candidate:** isolate ray–box intersections or BVH traversal with identical rays and hit outputs. Keep full stochastic rendering separate, with a documented statistical error criterion rather than an inappropriate byte-identical image requirement.

### R02. Decimo — arbitrary precision, carry chains, and Python extensions

**Repository:** https://github.com/forfudan/decimo

**Recent activity:** September 4, 2026 at 21:07 UTC, September 5 in Taipei. Commit: https://github.com/forfudan/decimo/commit/1f9696ee0b88172fc0e7804a5c35fa35cce21dd3

Decimo provides Mojo integer/decimal types, a calculator, and Python bindings. The inspected commit message describes eliminating an allocating negated temporary during subtraction and interleaving carry chains for addition. Importantly, its author says faster addition did not translate into faster multiplication/division in the measured workloads.

**Why read it:** a concrete optimization story involving arithmetic dependency chains, allocation, and native-versus-extension execution—not just a language scoreboard.

**Research candidate:** compare equal-width limb addition across sizes, validating carry propagation against a big-integer oracle. Measure standalone native execution and Python-call overhead separately; do not extrapolate addition improvements to an entire numeric library.

### R03. EmberJson — lazy, typed deserialization

**Repository:** https://github.com/bgreni/EmberJson

**Status:** discovery; README inspected, no new release date asserted.

The documented API supports mixing eager fields with lazy wrappers that retain grammar-validated input spans and materialize on access. Origin parameterization ties those spans to the source string's lifetime.

**Why read it:** a different design question from SIMD scanning: how much work can an application avoid when it only needs part of a document?

**Research candidate:** compare selective field access and full materialization as separate contracts. Check identical extracted values and malformed-input behavior; never compare lazy partial extraction against a full DOM and label the result a general parser speedup.

### R04. mojo-audio — FFT, spectrograms, and MAX-based audio inference

**Repository:** https://github.com/itsdevcoffee/mojo-audio

**Status:** discovery; repository documentation inspected, toolchain compatibility not executed.

The project separates a Mojo DSP layer—FFT, mel spectrograms, resampling, voice activity detection, and pitch processing—from Python/MAX inference components. Its README also distinguishes a C-compatible shared-library interface from the model pipeline.

**Why read it:** audio adds regular numerical kernels, streaming latency, and signal-quality requirements to the radar.

**Research candidate:** isolate one FFT or mel-filterbank stage, using the same dtype, input, windowing, normalization, and thread count. Validate numerical tolerances before timing. Treat the project's advertised speedups as replication targets, not this repo's results.

### R05. mojo-raylib — a practical 2D/3D integration path

**Repository:** https://github.com/kivicode/mojo-raylib

**Status:** discovery; README and generation workflow description inspected.

These raylib bindings are generated along with a C shim. The README explicitly distinguishes generated API coverage from manual testing: not every covered API has been manually exercised. It provides a basic-window example and a regeneration consistency check.

**Why read it:** a useful starting point for games and interactive graphics without first implementing a rendering engine.

**Research candidate:** compare batched versus individual boundary calls using the same raylib revision and workload. Test representative struct layouts and resource lifetimes first; binding coverage alone does not establish runtime correctness.

### R06. MAV — FFmpeg interoperability for audio/video

**Repository:** https://github.com/josiahls/mav

**Status:** discovery; README inspected.

MAV deliberately provides low-level FFmpeg bindings, not a high-level media framework. Its documentation includes image and video decode/encode examples and explicit native-library linking requirements.

**Why read it:** ownership of frames, pixel-format conversion, and native buffering are systems problems that general kernel comparisons miss.

**Research candidate:** separate native codec time, format conversion, and buffer copying when measuring a pipeline. Match codec settings and validate decoded data; a Mojo wrapper is not a Mojo reimplementation of FFmpeg.

### R07. mojo_libclang — source tooling and generated ABI tests

**Repository:** https://github.com/MoSafi2/mojo_libclang

**Status:** discovery; README inspected.

The library offers a clang.cindex-like Mojo interface to libclang for parsing C/C++, walking cursors, querying types, and reading diagnostics. Its regeneration procedure updates low-level bindings, layout tests, and a C shim together.

**Why read it:** it suggests tooling for automated binding generation and source analysis, not merely application runtime work.

**Research candidate:** measure a fixed AST traversal with the same libclang build, separating parser time from wrapper traversal. Verify record layouts and extracted declarations before comparing boundary overhead.

### R08. ish — bioinformatics-style alignment and fuzzy record filtering

**Repository:** https://github.com/BioRadOpenSource/ish

**Status:** discovery; README/CLI contract inspected. The package catalog lists an older Mojo requirement; current compatibility needs a fresh build.

`ish` filters records using alignment scores, including local/semi-global algorithms, configurable scoring matrices, line/FASTX records, and batching.

**Why read it:** sequence alignment introduces dynamic programming and data-dependent computation, broadening the current string parsing and hash-table emphasis.

**Research candidate:** extract a small alignment kernel with fixed scoring/gap rules and an independent reference. Separate parsing, batching, and scoring costs; validate exact scores and boundary conditions.

### R09. Strata — ML estimators, dense/sparse data, and native-library boundaries

**Repository:** https://github.com/ethqnol/Strata

**Status:** discovery; README inspected.

Strata documents scikit-learn-compatible estimators, dense/sparse containers, serialization, and pipelines. Some linear algebra routines use LAPACK/BLAS; these are not all pure Mojo kernels.

**Why read it:** it offers preprocessing and sparse workloads beyond LLM inference and shows why underlying numerical libraries must be disclosed in a language comparison.

**Research candidate:** choose one preprocessing transform or sparse operation, matching dtype, layout, thread count, and validation tolerance. Keep native BLAS/LAPACK-backed cases distinct from Mojo-implemented loops.

### R10. Kelvin — dimensional analysis as a compile-time abstraction experiment

**Repository:** https://github.com/bgreni/Kelvin

**Status:** discovery; README inspected.

Kelvin expresses quantities and dimensions through compile-time type parameters and unit ratios.

**Why read it:** a useful example of Mojo's type system serving scientific correctness, independent of GPU throughput.

**Research candidate:** compare a typed quantity expression against an equivalent scalar expression. Check units and values, then inspect generated assembly, code size, and compilation cost. Zero runtime overhead is a hypothesis to test, not a result established by this inventory.

### R11. mtest — observable test failures, crashes, and timeouts

**Repository:** https://github.com/mikeleppane/mtest

**Status:** discovery; README inspected.

The test runner documents supervised execution, distinct crash/timeout/compile-error outcomes, bounded crash attribution, and explicit flaky verdicts. It avoids silently treating a later successful retry as an ordinary clean pass.

**Why read it:** nightly compiler experiments need truthful failure classification before any performance comparison is meaningful.

**Research candidate:** build a small fixture set of pass/assertion-failure/crash/timeout programs and verify the runner's machine-readable outcomes and exit codes. This would be a correctness/methodology experiment, not a compiler-speed claim.

### R12. mojo-js — a browser-facing source-language prototype

**Repository:** https://github.com/exergy-connect/mojo-js

**Status:** discovery; proof of concept, not the official Mojo compiler in a browser.

The project tokenizes a supported Mojo subset, parses an AST, emits JavaScript, and executes it with a small runtime. Its README lists supported constructs and tests.

**Why read it:** an unconventional language-tooling direction that a Mojo-only language-filter search can miss because the implementation is JavaScript.

**Research candidate:** compare semantics for a small supported corpus against the official toolchain. Record unsupported constructs explicitly. Do not present this as full Mojo compatibility, native Mojo performance, or an official WebAssembly backend.

## B. Original articles, papers, and guides — 9 reading selections

### A01. Structured Mojo Kernels — architecture rather than release notes

**Source:** https://www.modular.com/structured-mojo-kernels

**Publication window:** March 5–April 3, 2026; a four-part series, counted once here.

The series introduces TileIO, TilePipeline, and TileOp and discusses composition and hardware portability. Read for separation of data movement, pipeline scheduling, and arithmetic. A future experiment could compare equivalent monolithic and composed kernels, measuring generated code and actual runtime rather than assuming abstraction is free. Older technical reading, not today's announcement.

### A02. Matrix Multiplication on Blackwell

**Source:** https://www.modular.com/matrix-multiplication-on-blackwell

**Publication window shown:** August–September 2025; series counted once.

A step-by-step kernel optimization reading path covering hardware features, pipelining, and scheduling. Its published hardware-specific results are historical author measurements. The transferable research idea is an optimization ladder with one changed mechanism per step; it is not evidence that an Apple or AMD kernel will receive the same speedup.

### A03. Mojo Miji — a maintained author's guide

**Source:** https://mojo-lang.com/miji/intro

**Revision:** the introduction lists an August 2026 revision.

Yuhao Zhu's guide covers the Python-to-Mojo transition, ownership, origins, SIMD, generics, and applications. It is useful for systematically filling conceptual gaps rather than chasing changelogs. Convert selected examples into version-pinned compile/runtime probes before reusing them; a maintained guide can still contain examples that drift.

### A04. When “Magic” Becomes Explicit: Mojo's Take on Metaprogramming

**Author/source:** Maxim Zaks, https://mzaks.medium.com/when-magic-becomes-explicit-mojos-take-on-metaprogramming-61bcfafc5145

**Published:** February 6, 2026.

An original explanation of compile-time reflection and default trait implementations for derived behavior. It offers a path to studying generated hashing/serialization versus handwritten equivalents. Re-check the article's older syntax and distinguish ideas presented as future features from features verified on the chosen toolchain.

### A05. From OpenCL towards Mojo GPU kernels in digital photo editing

**Author/source:** Max Chistokletov, https://forum.modular.com/t/from-opencl-towards-mojo-gpu-kernels-in-digital-photo-editing-first-look/2764

**Published:** February 24, 2026.

An original Darktable sigmoid-kernel experiment with a stated device/software setup and differing outcomes for two modes. It is a concrete non-AI GPU application. The proposed replication should validate the full output or a clearly justified numerical error metric, not just a few sampled pixels. This is an experiment/fork, not evidence that Darktable upstream adopted Mojo.

### A06. Bringing Blazing Fast State Space Models to the Modular MAX Framework

**Author/source:** Evan Owen, QWERKY AI, https://qwerky.ai/blog/bringing-blazing-fast-state-space-models-to-the-modular-max-framework

**Date:** the page displays `02/04/2026`; numeric date convention was not independently established in this scan. Treat as older reading, not current news.

The implementation narrative covers Mamba/SSM support, selective scan, causal convolution, and persistent recurrent-state caching in MAX. Useful for understanding how an execution framework's transformer assumptions differ from recurrent models. A small experiment could compare explicit state reuse against equivalent recomputation, with identical recurrence semantics.

### A07. Mojo: MLIR-Based Performance-Portable HPC Science Kernels on GPUs for the Python Ecosystem

**Paper:** https://arxiv.org/abs/2509.21039

**Published:** September 25, 2025.

The researchers study a seven-point stencil, BabelStream, miniBUDE, and Hartree–Fock against CUDA/HIP baselines on NVIDIA and AMD hardware. This expands the radar into scientific kernels, including memory-bound and atomic-heavy cases. Use its workload and methodology as replication material; do not import old toolchain results into a Mojo 1.x scoreboard.

### A08. MojoFrame: Dataframe Library in Mojo Language

**Paper:** https://arxiv.org/abs/2505.04080

**Published:** May 7, 2025.

The paper studies relational operations and cardinality-aware data representation, including filtering, joins, group-by, and UDFs. A useful next workload is a controlled join with explicit key cardinality and skew, rather than another undifferentiated CSV throughput number. Historical claims about ecosystem coverage apply to the paper's date, not today's catalog.

### A09. MojoR — a “Numba” for R

**Author discussion:** https://forum.modular.com/t/mojor-a-numba-for-r/2718

**Dated discussion:** February 2026.

The author describes transpiling R into Mojo, JIT compiling, and calling compiled functions in-process through R's `.Call` ABI using pointers and shape/stride metadata. This is an author-described prototype; a public repository was not established from the inspected thread, so none is invented here. Useful research directions include semantics, compilation latency, and call-boundary cost—not accepting the headline speedup without replication.

## D. Research candidates — options, not completed work

1. **Decimal carry-chain or temporary-allocation experiment:** motivated by Decimo's dated change; isolate one arithmetic mechanism.
2. **Lazy JSON access versus full materialization:** compare equal work contracts and validation behavior using EmberJson as a design reference.
3. **Ray–box/BVH primitive:** explore geometry with deterministic input/output rather than benchmarking a whole renderer first.
4. **FFT/mel-filterbank stage:** broaden into audio, holding dtype/windowing/threads constant and validating numerical error.
5. **Typed quantity abstraction:** compare Kelvin-style units with scalar code at both runtime and code-generation levels.
6. **Alignment or join workload:** add dynamic programming or cardinality/skew sensitivity beyond the existing hash/parser tasks.

The integrated research phase still selects **exactly one** feasible, verified task. Discovery does not have to be limited to that task's domain.
