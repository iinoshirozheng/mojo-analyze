## A. Current official developments — 4

### O01. Nightly has already moved beyond the 1.1 release branch: Mojo 1.2 / MAX 26.7

**Freshness:** recent development, 2026-09-12.  
**Source:** https://github.com/modular/modular/commit/dafad186fb3d5e9e721ef3de33881f386f07ced8

The public Modular tree now pins **Mojo `1.2.0.dev2026091205` and MAX `26.7.0.dev2026091205`**. Yesterday's brief was still tracking the 1.1 / 26.6 nightly line, so this is a real version-line transition rather than another date-only pin.

**Why it matters:** `mojo-analyze` now has three useful toolchain lanes conceptually: stable 1.0 for canonical numbers, the 1.1 release line when a stable artifact appears, and the 1.2 development line for advisory compiler-drift probes. The exact package revision must stay part of benchmark provenance.

### O02. Mojo source is migrating from forced/no-inline decorators toward `@inline`

**Freshness:** recent development, 2026-09-12.  
**Source:** https://github.com/modular/modular/commit/0eeb9c145e2539cb5aab8a3085b4853d27440d26

A tree-wide change replaces `@always_inline` and `@no_inline` usage with `@inline`. That is technically relevant to this repository because Category E previously established that forced inlining of byte-scanning helpers materially changed performance on the pinned 1.0 toolchain.

**Evidence boundary:** this commit establishes an API/compiler-policy migration, not that the same Category-E speedup will survive under 1.2. A future migration probe should compare generated calls/assembly rather than assuming decorator names preserve identical optimization semantics.

### O03. Advanced fusion fixed a silent correctness bug for non-unit-stride tensors

**Freshness:** recent development, 2026-09-12.  
**Source:** https://github.com/modular/modular/commit/04f9b20d8ed4539e3f0267d5a126790fd85065cd

Advanced fusion previously reconstructed one class of captured tensors through a path that assumed unit inner stride. Fusing a transpose or non-unit slice into a vectorized consumer could therefore read the wrong elements without necessarily crashing. The new path preserves layout and selects contiguous load, splat, or gather based on stride.

**Why it matters:** this is a strong reminder that a fast fused graph needs stride/layout correctness gates, not merely final timing. A useful reproduction would compare contiguous, zero-stride/broadcast and non-unit-stride views with a non-fused reference before timing fusion.

### O04. MAX engine benchmarks can now use Zipf and real-token distributions

**Freshness:** recent development, 2026-09-12.  
**Source:** https://github.com/modular/modular/commit/7de617695dd8b2527a19a6cb73cbf00a18ef29cd

The engine benchmark previously used uniformly random token IDs, which can distribute MoE expert routing more evenly than real traffic. A new `TokenSource` abstraction adds `uniform`, `zipf`, and InstructCoder-derived token distributions.

**Why it matters:** input distribution is part of the benchmark contract when it changes load balance. This generalizes beyond LLM serving: a benchmark that hides skew can mischaracterize hash tables, caches, branch predictors or schedulers just as easily as MoE routing.

## B. Repository discoveries — 12

### R01. `nabla-ml/nabla` — lazy scientific/ML execution with Mojo custom kernels

**Domain:** scientific computing / autodiff / distributed GPU.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/nabla-ml/nabla

Nabla combines a high-level Python API, a lazy MAX-native execution model, autodiff, device meshes/SPMD sharding, and custom Mojo kernels. The repository currently requires Modular nightly, which is an important compatibility boundary.

**Why it matters:** this is a realistic example of Mojo as the low-level kernel language inside a higher-level scientific runtime rather than a whole-application replacement for Python.

**Research angle:** isolate one custom kernel and measure kernel execution separately from graph tracing, compilation, sharding and collective communication.

### R02. `DataBooth/mojo-dotenv` — compatibility-first parser development

**Domain:** configuration parsing / compatibility testing.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/DataBooth/mojo-dotenv

The project implements modern `.env` parsing in Mojo and explicitly validates behavior against `python-dotenv`, including variable expansion, quoting, multiline values and escape sequences. Its README reports 49 tests and 98%+ compatibility; those are project claims, not independently audited here.

**Why it matters:** a mature reference implementation can serve as a semantic oracle while a Mojo-native parser evolves.

**Research angle:** use the same fixture corpus to compare parser correctness first, then profile specific branches such as quoted/multiline expansion rather than timing only a happy-path file.

### R03. `mzaks/mojo-csv` — RFC-4180 CSV with optional SIMD tokenization

**Domain:** parsing / SIMD.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/mzaks/mojo-csv

The library exposes RFC-4180 reading/writing and a switchable SIMD tokenizer. The README reports about a 20% tokenizer improvement from SIMD and sub-3-second parsing/tokenization for 1 GiB on an Apple M1; these are historical author measurements.

**Why it matters:** unlike `mojo-analyze` Category D, this project separates CSV tokenization as a reusable concern and therefore offers a cleaner candidate for structural delimiter-scan experiments.

**Research angle:** compare scalar and SIMD tokenization on the same generated RFC-4180 corpus with identical token boundaries/checksum, varying quote density and field length.

### R04. `lczerniawski/crypto` — native hashing and secure-random primitives

**Domain:** cryptography / byte-oriented kernels.  
**Freshness:** newly discovered existing project; work in progress.  
**Repository:** https://github.com/lczerniawski/crypto

The current library contains MD5 and SHA-1 plus secure random integer generation and is distributed through modular-community. It explicitly labels itself a work in progress.

**Why it matters:** fixed-block hash transforms provide byte/integer workloads with strong standard test vectors, making correctness much easier to enforce than ad-hoc performance examples.

**Research angle:** a future SHA-1 compression-block microbenchmark could compare generated rotate/XOR/add code across Mojo and C while using published digest vectors as the oracle. Security suitability of MD5/SHA-1 is separate from their usefulness as deterministic kernels.

### R05. `lczerniawski/uuid` — RFC-9562 identifiers as a correctness-heavy systems library

**Domain:** identifiers / parsing / random generation.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/lczerniawski/uuid

The project describes UUID generation, parsing, validation and formatting in RFC-9562-compatible string forms.

**Why it matters:** identifier libraries combine parsing, formatting and randomness, where throughput alone is not enough; conformance and distribution properties matter.

**Research angle:** benchmark parse/format separately from random generation and validate against RFC vectors. Do not treat RNG-backed UUID generation as a deterministic language-speed microbenchmark.

### R06. `fourlexboehm/mojo-lambda-runtime` — Mojo on AWS Lambda without libcurl

**Domain:** serverless / sockets / deployment tooling.  
**Freshness:** newly discovered existing project; package 0.1.0 was published to modular-community recently.  
**Repository:** https://github.com/fourlexboehm/mojo-lambda-runtime

The runtime implements AWS Lambda's Runtime API over plain HTTP using libc sockets and provides a project scaffold for `provided.al2023` / arm64 deployment. Packaging deliberately separates the importable `.mojopkg` from generated app-owned Docker/build/deploy files.

**Why it matters:** it tests Mojo in a constrained systems deployment where startup, binary/package compatibility and network boundary costs may matter more than tight-loop throughput.

**Research angle:** measure cold-start initialization separately from handler execution and network/runtime-API waits; otherwise AWS environment latency will swamp language/runtime effects.

### R07. `msaelices/mojo-libc` — system-call access as a reusable FFI layer

**Domain:** systems programming / libc FFI.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/msaelices/mojo-libc

This package wraps libc functions for Mojo, including socket-level APIs used by higher-level systems packages.

**Why it matters:** a shared libc layer can prevent each networking/system project from rebuilding ad-hoc bindings, but ABI layout and platform differences become the primary correctness contract.

**Research angle:** validate representative structs/constants against a tiny C oracle before measuring call overhead; FFI speed is meaningless if layout parity is assumed rather than tested.

### R08. `msaelices/claude-mojo-skills` — external agent skills for Mojo migration and kernels

**Domain:** developer tooling / agent-assisted engineering.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/msaelices/claude-mojo-skills

The repository packages Mojo-specific agent skills for GPU kernels and version migration, explicitly acknowledging rapid Mojo API drift and the need to verify generated code against current docs/toolchains.

**Why it matters:** this is ecosystem tooling rather than a runtime library. It reinforces that version-aware compile/test feedback should be part of automated Mojo code generation.

**Research angle:** evaluate a migration skill on a pinned old example set and score build/test success, not prose quality or token count alone.

### R09. `fnands/mimage` — image parsing with an explicit native-vs-zlib boundary

**Domain:** image processing / file formats / FFI.  
**Freshness:** newly discovered older project.  
**Repository:** https://github.com/fnands/mimage

Mimage aims at Pillow-like image reading/writing in Mojo. An open design boundary is PNG decompression: the project historically calls zlib rather than pretending the entire pipeline is pure Mojo.

**Why it matters:** it is a good case study in attribution. Image decoding time must be decomposed between format parsing, checksum/filter stages and native decompression before making language-level claims.

**Research angle:** measure PNG filter reconstruction separately from zlib and file I/O, with decoded-pixel equality as the oracle.

### R10. `msteele/mojo-sdl` — minimal SDL2 binding and interactive Mandelbrot

**Domain:** graphics / windowing / FFI.  
**Freshness:** newly discovered older project.  
**Repository:** https://github.com/msteele/mojo-sdl

This small binding exposes SDL2 to Mojo without Python at runtime and includes an interactive Mandelbrot example.

**Why it matters:** it shows a lower-level graphics route distinct from WebGPU/wgpu-mojo: use a mature C window/input library and keep computation in Mojo.

**Research angle:** measure render/update boundary overhead only after separating it from Mandelbrot compute; a frame benchmark that mixes both cannot attribute cost to the binding.

### R11. `helehex/infrared` — geometric algebra as a non-string numerical workload

**Domain:** numerical/scientific computing / geometry.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/helehex/infrared

Infrared is a geometric-algebra project for Mojo, representing a domain with small structured algebraic objects rather than large tensors or text parsing.

**Why it matters:** geometric products/rotors can expose compile-time specialization and SIMD behavior without inheriting the parser/hash-table confounds of Categories C–E.

**Research angle:** choose one fixed-dimension product with a trusted scalar reference, inspect generated code, then scale dimensions only after correctness and operation counts are clear.

### R12. `YichengDWu/matmul.mojo` — BLIS-style CPU matrix multiplication in pure Mojo

**Domain:** CPU linear algebra / threading / cache blocking.  
**Freshness:** newly discovered older technical project.  
**Repository:** https://github.com/YichengDWu/matmul.mojo

The project implements a multithreaded BLIS-style matrix multiplication rather than relying on an external BLAS call.

**Why it matters:** it gives a CPU cache-blocking/threading reference complementary to recent GPU-heavy Mojo work.

**Research angle:** any replication must match matrix dtype, dimensions, thread count, packing strategy and warm-cache policy; a BLAS comparison without those controls is not a compiler comparison.

## D. Deep-dive picks

1. **Mojo 1.2 nightly + inline-policy migration** — particularly relevant to `mojo-analyze` because its Category-E optimization story used `@always_inline` on Mojo 1.0. The correct follow-up is a version-pinned codegen probe, not an automatic source rewrite.
2. **Stride-aware advanced fusion correctness** — a concrete example where performance-oriented fusion silently violated layout semantics; future GPU benchmarks should include non-contiguous correctness fixtures.
3. **`mojo-csv` SIMD tokenizer** — offers a way to isolate delimiter/quote scanning from the hash/probe/aggregation stack that dominates Category D.
4. **`nabla` custom-kernel boundary** — a useful real-world decomposition of high-level Python/autodiff orchestration and low-level Mojo kernel execution.

## E. Ranked research candidates

1. **Fixed-width FNV codegen differential** — yesterday's controlled workload found Mojo about 6% behind C on Linux x86_64 but about 36% behind on Linux arm64. Emit optimized assembly for both implementations on both architectures and compare the actual 32-byte hash loop before inventing another source rewrite.
2. **CSV delimiter-scan micro-workload** — derive a checksum-verifiable scalar/SIMD tokenizer inspired by `mojo-csv` to isolate parsing from FNV and probing.
3. **Mojo 1.0 vs 1.2 inlining migration** — compile the existing Category-E scanning helpers under pinned stable/nightly toolchains and check whether the new `@inline` semantics preserve the call-free hot path.
4. **Input-skew methodology probe** — build a synthetic fixed-size hash/probe workload with uniform and Zipf key distributions to quantify how much distribution changes collision/probe behavior.
5. **Stride-correctness fixture** — add a small GPU research case with contiguous, broadcast and non-unit-stride views before measuring fusion.
