# Mojo Ecosystem Radar — 2026-09-03

Delta-focused brief: this report records substantive developments since the 2026-09-02 radar rather than repeating yesterday's Mojo 1.0/open-source background.

## Official Mojo / Modular changes

### Mojo 1.1 development has started in the public tree

The `modular/modular` repository pinned its lockfiles today to `Mojo 1.1.0.dev2026090305` and `MAX 26.6.0.dev2026090305`. This is a nightly/dev build, **not a stable Mojo 1.1 release**, but it is the clearest public signal that post-1.0 work is now moving on the 1.1 line.

Why it matters for `mojo-analyze`: the repo currently pins stable `mojo >=1.0.0,<2`. The new dev line makes a stable-vs-nightly differential benchmark practical: keep canonical numbers on stable, then periodically run the exact same checksum-gated suite against the nightly compiler to detect codegen regressions or wins before they reach a point release.

Source:
- https://github.com/modular/modular/commit/93f66d10ebd5ee4ad860562594253713ea1c3738

### A Mojo contribution guide landed after the compiler open-source release

Modular added a dedicated Mojo contribution guide today. This is a small documentation change compared with the compiler opening itself, but it matters because the open compiler is now becoming an actively contribution-oriented project rather than merely source-visible.

### Compiler-internal constraint diagnostics continue to simplify

Two `mojo-lang` commits simplify the compiler's conversion/conformance failure plumbing: `canMetaTypeUpCastTo` can now return a detail-carrying `ConstraintResult` when needed, while `canZeroCostConvert` drops an older failure out-parameter. These are compiler-internal changes rather than new source-language syntax, so no benchmark migration is justified yet.

## MAX / GPU: unusually strong performance signals today

### MoE routing: one CTA replaces one CTA per expert

A new routing-index kernel changed the work decomposition from one CTA per expert to one CTA for the routing operation. It builds a shared-memory expert histogram, performs block-wide prefix scans, then scatters tokens. Modular reports the routing kernel itself as **1.8x–7.9x faster** depending on token distribution/count, with Inkling-Small-NVFP4 decode step time improving from **13.75 ms to 12.91 ms**.

Why interesting: this is a particularly clean example of an algorithmic/work-decomposition win rather than instruction-level tuning. Work scales primarily with tokens instead of tokens × experts.

Potential `mojo-analyze` experiment: add a synthetic histogram→prefix-scan→scatter workload with two structurally different implementations and sweep `items × groups`. It could test when reducing launch/work decomposition dominates lower-level kernel tuning.

Source:
- https://github.com/modular/modular/commit/768fd6bae1b7805b0ec7ba935ad2fd93e8ca4f13

### AMD MoE prefill: persistent kernels remove mostly-empty workgroups

For two MXFP8 grouped-GEMM prefill bands, Modular replaced grids sized from a capacity bound with persistent kernels sized to the machine and grid-striding over actual routed tiles. On an 8-GPU prefill benchmark, reported median launch time fell **36.7%** for gate/up and **46.3%** for down projection; each produced roughly **3% end-to-end prefill improvement**. The commit explicitly says unchanged control kernels stayed flat.

Why interesting: this is good benchmark methodology as well as a performance result—kernel-local gains are separated from end-to-end gains, with controls kept unchanged.

Potential experiment: a GPU `useful work density` benchmark that varies the ratio of active work to launched capacity and compares static-grid vs persistent-grid scheduling.

Source:
- https://github.com/modular/modular/commit/eb2deef8303b876ac9e3468cf9d83b39bc5dbf92

### AMD sampling gains a portable cross-block cooperation primitive

`CoopRow` was added as a cross-block row group based on publish slots plus a device-scope atomic barrier, intended to stand in for NVIDIA thread-block-cluster functionality on CDNA. The implementation aborts if bounded waiting expires rather than risking a silent wrong result when blocks are not co-resident. Related top-k/top-p and Gumbel work now splits wide rows across blocks on AMD to improve compute-unit occupancy while preserving exact sampling behavior.

Why interesting: this is a concrete portability pattern—same high-level decomposition, different synchronization primitive because hardware capabilities differ.

Potential experiment: compare single-block vs cooperative multi-block reductions across row widths, while checksum-gating exact integer/reduction variants. This would complement `mojo-analyze`'s current CPU-vs-GPU work with a GPU decomposition study.

Sources:
- https://github.com/modular/modular/commit/f9eb8cba7736b14033dbcdc1b2a5a1c0b97c2e62
- https://github.com/modular/modular/commit/3df818467b2c1b4c36bf8e3dc3d11aa22e5409a7
- https://github.com/modular/modular/commit/66a74d220589dcff1eb0a23ff2a8145802038ad2

### Correctness testing is becoming more concurrency-aware

The M3 decode path gained a determinism oracle that launches multiple concurrent executions before synchronization, plus a batch-invariance oracle that requires one request's scores/selected blocks to remain bit-identical under different co-batch compositions. Separately, top-k/top-p fuzzing now covers BF16 and production-scale vocabulary widths.

Why interesting: GPU correctness cannot be reduced to one successful checksum on one launch shape. Scheduling, batching, precision, and concurrency can expose bugs that single-shot tests miss.

Potential `mojo-analyze` methodology improvement: for future GPU benchmarks, add a reproducibility mode that repeats kernels under varied batch/launch composition and asserts deterministic output when the algorithm promises determinism.

Sources:
- https://github.com/modular/modular/commit/c81c179a701ad52dea147793c8933fe2fda83beb
- https://github.com/modular/modular/commit/ed59b7b00da2f575736df8949ca25e294c42df46

### MAX profiling and serving also surfaced useful measurement lessons

`profile_scope` can now carry NVTX colors for in-region profiling ranges. More strikingly, restoring graph-capture memory headroom in one serving planner traded about **12% KV-cache capacity** for a reported **~90% throughput improvement** on a paired 8×B200 GLM-5.3 NVFP4 test (0.33→0.63 req/s, with large TTFT/TPOT/inter-token-latency improvements).

Why interesting: the serving result is a reminder that peak memory efficiency can reduce throughput if it destroys capture/scheduling headroom. This is not directly a `mojo-analyze` microbenchmark candidate, but it is a strong example of measuring system-level tradeoffs rather than optimizing one resource in isolation.

Sources:
- https://github.com/modular/modular/commit/2249a0615202a8df178cc3bcc099ad4c54074979
- https://github.com/modular/modular/commit/f61ad4669248411ff2f5d200b6ebcfec5ae5e7dd

## Active community repositories

### `tamnd/mojo.httpx` — real networking work is exposing Mojo async compiler limits

Repository: https://github.com/tamnd/mojo.httpx

Today the project documented a seventh async limitation while designing its connection pool. Its probes establish that three sequential suspending loops, conditionally skipped loops, and guarded early returns can work, but certain dereferences used by a guard can fail lowering with `operand #0 does not dominate this use`; an inline form can even crash the compiler. A discarded task handle in the coroutine frame can trigger another dominance failure. The project records synchronous-helper/scalar-state workarounds rather than hiding them inside library code.

Why interesting: this is exactly the kind of systems-programming pressure that toy Mojo examples do not exercise. It gives small, real-world compiler-regression cases around async frame lowering and value dominance.

Potential `mojo-analyze` experiment: create a `compiler-probes/async/` track that compiles minimal known-good/known-bad coroutine shapes against stable and nightly Mojo. This is not a runtime benchmark, but it would make the new stable-vs-nightly longitudinal idea useful for compiler correctness too.

The same project also hardened its networking tests for Windows 11/WSL2; the reported run reached **1531 passing tests**, another signal that Mojo networking libraries are moving into cross-platform edge cases rather than just basic socket demos.

Sources:
- https://github.com/tamnd/mojo.httpx/commit/a86c34007238f0bdfb00e0728752d6d3f66b647f
- https://github.com/tamnd/mojo.httpx/commit/4bb97a2989396f4a82e48e19598567ad8d196b67

### `codetalcott/mojo-http` — release 0.17.0

Repository: https://github.com/codetalcott/mojo-http

`mojo-http` released **0.17.0** today. The project is a Mojo HTTP application server with WSGI/ASGI-oriented integration and real-time features; surrounding release work also added more observable canary/watchdog behavior for integration testing.

Why interesting: together with `mojo.httpx`, this gives the ecosystem both increasingly serious client-side and server-side HTTP work. Networking is becoming a credible future systems workload for Mojo benchmarking once interfaces/toolchain behavior stabilize enough to keep a comparison fair.

Potential experiment: later, define a localhost fixed-payload HTTP throughput/latency workload separating parser cost, socket/syscall cost, and framework overhead. Do not add it to the canonical suite yet—the async/compiler surface is still moving quickly.

### `bewaffnete/MojoVec` — worth adding to the systems/data watchlist

Repository: https://github.com/bewaffnete/MojoVec

Newly surfaced in today's ecosystem search, MojoVec is a Mojo-native vector database with flat and SQ8 HNSW indexes, SIMD distance paths, BM25 + hybrid retrieval, bitmap metadata indexes, persistence/WAL recovery, and Python interop. Its stated technical question—whether Mojo can approach hand-tuned C++ SIMD performance for vector search—is unusually aligned with this repository's purpose.

Why interesting: this is much richer than a one-function SIMD demo. HNSW introduces branch-heavy graph traversal, vector distance kernels, memory locality, quantization, and persistence around the same system.

Potential experiment: extract only the distance-search kernel first: brute-force L2/cosine over fixed-dimensional vectors in Mojo/C/Rust, scalar vs explicit SIMD, checksum/neighbor-order verified. HNSW itself should come later because implementation-policy differences make cross-language fairness harder.

Source:
- https://github.com/bewaffnete/MojoVec

## What changed from yesterday

Yesterday's radar was mostly about establishing the post-1.0 landscape: open compiler, SIMD/GPU JSON, DuckDB/Arrow, LLM kernels, FFI and portability projects. Today's delta is different:

1. **The public nightly is already on the Mojo 1.1 development line.**
2. **Open-source Modular commits now expose unusually detailed optimization evidence**, including kernel-local and end-to-end numbers.
3. **GPU correctness work is explicitly testing determinism and batch invariance**, suggesting stronger methodology for future `mojo-analyze` GPU work.
4. **Mojo networking is stressing async lowering in real applications**, producing small compiler-regression probes that can be tracked across versions.
5. **A vector database (MojoVec) provides a promising future real-world SIMD/memory workload**, but should be reduced to a fair primitive before inclusion.

## Research candidates

1. **Stable vs nightly Mojo differential lane** — run existing checksum-gated categories against stable Mojo and a pinned nightly (`1.1.0.dev...`) without replacing canonical stable results. Track compile success, runtime, binary/codegen changes, and regressions over time.
2. **Async lowering regression probes** — reduce the `mojo.httpx` dominance failures into tiny stable/nightly compile probes. This turns ecosystem breakage into longitudinal compiler evidence.
3. **GPU useful-work-density experiment** — static capacity-sized launch vs persistent/grid-stride launch while sweeping active-work density, inspired by Modular's AMD MoE result.
4. **GPU determinism stress mode** — repeat deterministic kernels under varied batch/launch composition, borrowing the new Modular batch-invariance methodology.
5. **Vector-search primitive** — fixed-dimension brute-force L2/cosine in Mojo/C/Rust, scalar and explicit SIMD, based on the technical question behind MojoVec; defer full HNSW comparison until fairness constraints are clear.
