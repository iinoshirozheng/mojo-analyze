### O01 — Sep-17 nightly advances to Mojo `1.2.0.dev2026091705` / MAX `26.7.0.dev2026091705`

**Lane:** recent development — 2026-09-17.  
**Source:** https://github.com/modular/modular/commit/975baa793c02665a36194c285496e133c9452068

The public Modular tree advanced its lockfiles by one nightly from Sep-16. This is provenance, not a performance result.

**Why it matters:** stable Mojo 1.0 remains the canonical benchmark lane. Compiler-drift work should pin the exact nightly package revision and source SHA rather than infer behavior from the calendar date.

**Experiment angle:** only use the 1.2 nightly in a narrowly scoped stable-vs-nightly differential where source, workload, checksum, and compiler flags remain fixed.

### O02 — zero-cost convertible closures receive a correctness fix

**Lane:** recent development — 2026-09-17.  
**Source:** https://github.com/modular/modular/commit/0cc0cca06b6950f5bb99e77e9aa02b86e7bdbb1e

The compiler fixes handling of a zero-cost convertible closure. This sits in the same general closure/function-conversion area that has changed substantially across the 1.0 stabilization cycle.

**Why it matters:** closure representation is both a correctness and codegen boundary. A source-level closure that looks allocation-free should not be assumed to lower to the same ABI/function-pointer form across compiler revisions without inspection.

**Experiment angle:** a compile/codegen corpus could compare stateless, captured, `thin`, and convertible closures across stable 1.0 and a pinned 1.2 nightly; correctness and ABI shape come before timing.

### O03 — `Span` gains explicit uninitialized-memory methods

**Lane:** recent development — authored 2026-09-16, landed in the Sep-17 public tree.  
**Source:** https://github.com/modular/modular/commit/06581d8784f309cea79d22ca51dc33c068de490a

The standard library adds methods for working with uninitialized memory through `Span`.

**Why it matters:** initialization policy can materially change low-level benchmark cost, but it is also part of the semantic contract. Recent `mojo-analyze` raw-storage experiments already showed why accidentally skipping initialization invalidates a comparison.

**Experiment angle:** if these APIs are used later, compare fully initialized and intentionally uninitialized construction only when both implementations expose the same observable semantics; never count omitted initialization as a language speedup.

### O04 — Qwen3.5 recurrent state is moved back to per-layer selection

**Lane:** recent development — 2026-09-17.  
**Source:** https://github.com/modular/modular/commit/24fbc8ab2d226647ce68a5eebbd9d4955aac5402

A Qwen3.5 linear-attention bug caused layers sharing a compiled subgraph to read/write the same recurrent-state row because the layer-dependent selection had been captured in the shared body. The fix moves row selection back to the call site so each layer carries its own reduced row ID while preserving the exported graph signature.

**Why it matters:** graph sharing can accidentally capture state that should vary per logical layer. A model can remain numerically plausible enough to run while being semantically wrong (the commit describes fluent nonsense), so shape/signature checks alone are insufficient.

**Experiment angle:** for stateful graph reuse, add fixtures that permute layer/request identity and verify independent state evolution before benchmarking shared-subgraph optimizations.

## 2. Repository discoveries / deep dives — 12

### R01 — `itsdevcoffee/mojo-audio`: DSP + MAX voice pipeline

**Repository:** https://github.com/itsdevcoffee/mojo-audio  
**Domain:** audio/DSP / MAX / FFI  
**Lane:** newly surfaced existing project.

The repository combines Mojo FFT/STFT, mel spectrograms, resampling, VAD, pitch shifting, iSTFT and WAV I/O with Python/MAX Graph inference for HuBERT/ContentVec and RMVPE. It also exposes a C-compatible Mojo DSP shared library. The README documents an optimization path from a naive FFT/mel implementation to SIMD/radix-4/multicore code.

**Evidence boundary:** the published 20–40% mel-spectrogram advantage over librosa and the larger optimization journey are author-reported, not reproduced here; the project still documents an older Mojo 0.26+ requirement.

**Research angle:** a fixed-size FFT or mel-filterbank stage with a numerical oracle would add a non-string workload and permit source/codegen inspection independent of MAX model execution.

### R02 — `RyanLeber/fire-physics-engine`: 2D rigid-body demo with explicit FFI pain points

**Repository:** https://github.com/RyanLeber/fire-physics-engine  
**Domain:** game/physics / raylib FFI  
**Lane:** newly surfaced existing prototype.

This Box2D-lite-inspired Mojo engine implements a 2D physics demo and calls out FFI limitations as its largest constraint, including raylib structs and `DLHandle` plumbing. The project explicitly labels itself a demo and nightly-only.

**Why it matters:** it exposes a realistic split between simulation math and graphics binding overhead rather than presenting a monolithic “game engine benchmark.”

**Research angle:** benchmark collision/integration kernels headlessly with deterministic final-state checks; keep raylib and display work outside the measured physics kernel.

### R03 — `bgreni/EmberJson`: simdjson-style immutable tape path in pure Mojo

**Repository:** https://github.com/bgreni/EmberJson  
**Domain:** parsing / SIMD / data structures  
**Lane:** newly surfaced existing project.

`parse_document` uses a SIMD structural-index stage feeding an iterative stage-2 walker, stores containers as tape spans, and uses one shared string arena rather than per-node allocation.

**Why it matters:** this gives Category E a useful external design comparison: structural scanning, tape construction, and materialization are separable stages.

**Research angle:** replicate only the structural-index contract on the existing deterministic JSON corpus before considering end-to-end parser comparisons.

### R04 — `gonsolo/Gonzales`: production-scale physically based rendering in Mojo

**Repository:** https://github.com/gonsolo/Gonzales  
**Domain:** graphics / GPU / geometry  
**Lane:** newly surfaced existing project.

Gonzales is a roughly 10k-line Mojo path tracer covering PBRT-v4 scene parsing, BVH construction/traversal, materials, wavefront GPU path tracing, film and à-trous denoising; its README targets Moana and the Bitterli scenes.

**Evidence boundary:** “production-capable” and performance implications are project claims; this run did not render a scene.

**Research angle:** isolate BVH traversal or one ray/triangle kernel with a fixed hit digest and compare CPU/GPU/codegen separately from scene parsing and denoising.

### R05 — `kivicode/mojo-raylib`: generated raylib v6.x bindings with regeneration checks

**Repository:** https://github.com/kivicode/mojo-raylib  
**Domain:** graphics / generated FFI  
**Lane:** newly surfaced existing project.

Bindings and a C compatibility shim are generated from raylib headers, while `regen-check` is intended to fail CI if regeneration would change committed output. The README claims generated API coverage but explicitly says not everything is manually tested.

**Why it matters:** generated bindings need two correctness layers: generator determinism and ABI/behavior validation. “100% generated coverage” is not the same as tested semantic coverage.

**Research angle:** choose a few struct/value-passing APIs and compare sizes, field offsets and return values with a tiny C oracle before measuring call overhead.

### R06 — `gabrieldemarmiesse/mojo-zlib`: Python-shaped zlib binding plus pure-Mojo checksums

**Repository:** https://github.com/gabrieldemarmiesse/mojo-zlib  
**Domain:** compression / C FFI / checksums  
**Lane:** newly surfaced existing project.

The package exposes zlib/gzip/raw-DEFLATE APIs, streaming operations, and pure-Mojo CRC32/Adler-32 while compression itself uses optimized zlib. Its README explicitly says the binding is not yet as fast as desired and is waiting on Mojo language features.

**Why it matters:** the library cleanly separates a native C codec from Mojo-side checksum/control logic, making attribution possible.

**Research angle:** CRC32/Adler-32 are deterministic byte kernels with standard vectors; compression throughput should be benchmarked separately from checksum and allocation/FFI overhead.

**Research angle:** compatibility/build migration is higher value than copying old benchmark numbers. If it builds, isolate one operator with an exact reference and current compiler provenance.

### R08 — `FarhanAliRaza/moonshine-mojo`: end-to-end speech recognition with Mojo GPU kernels

### R09 — `Jason-Hoford/mojo-fluid-sim`: SPH simulation plus explicit Mojo↔Python streaming boundary

## 5. Ranked research candidates

1. **Category-D scanner-only semantic cut (strongest existing next step).** Preserve file read + delimiter scanning + field-boundary bookkeeping, remove quantity/price digit accumulation, and run scanner-only beside the existing parser-only pair in the same x86_64/arm64 job. Cross-language checksums must validate equivalent field boundaries. This determines whether the remaining parser-prefix gap already exists before numeric parsing.
2. **`Span` initialization-policy microprobe.** On a future nightly lane, compare equivalent initialized storage construction paths and inspect whether the new uninitialized-memory APIs merely expose omitted work or enable cleaner codegen under equal semantics.
3. **EmberJson structural-index reproduction.** Port/replicate only structural indexing against the existing deterministic JSON corpus; require byte-identical structural positions before measuring scalar/SIMD variants.
4. **Generated raylib ABI oracle.** Verify representative generated structs and return-by-value calls against C before measuring FFI overhead.
5. **FFT codegen workload.** Use a fixed radix/power-of-two FFT from an external Mojo DSP project, validate against a high-precision reference, then inspect SIMD/vectorization and architecture differences.
