## 1. Important current developments

### O01 — Nightly moves to Mojo 1.2.0.dev2026091605 / MAX 26.7.0.dev2026091605

**Source:** https://github.com/modular/modular/commit/64fcd68cb5f49864e3e7987017bb1147e4e40a25  
**Lane:** recent development — 2026-09-16 UTC

The public `modular/modular` tree pins the September 16 nightly packages. This is one day newer than yesterday's `dev2026091505` baseline.

**Why it matters:** nightly experiments must pin exact package revisions; compiler/runtime behavior can change daily even when source-level benchmark code does not.

**Candidate:** keep stable Mojo 1.0 as the canonical lane and use 1.2 nightly only for narrowly scoped compiler/codegen drift probes.

### O02 — Mojo precompiled-package cache publication becomes atomic

**Source:** https://github.com/modular/modular/commit/10dcee01de95b335307a2cee2fc098946dad21bb

The compiler's shared precompiled-package cache was written directly to the final `.mojoc` path. Concurrent compiler processes could therefore observe a half-written package and fail with invalid magic bytes. The fix stages the output and publishes it with atomic rename.

**Why it matters:** this is a concrete reproducibility/CI lesson: package-cache corruption can masquerade as random compiler instability when multiple jobs share a cache path.

**Candidate:** if `mojo-analyze` ever parallelizes compilation, stress a shared-cache build with many identical compiler invocations and verify zero corrupt package reads. Do not benchmark compiler throughput until correctness under concurrency is established.

### O03 — Paged KV-cache TMA addressing fixes silent coordinate-overflow risk

**Sources:**
- https://github.com/modular/modular/commit/77472ccfdcc05f4f8592b810b26245a410290fc1
- https://github.com/modular/modular/commit/1f097fc76910fdac9f43291ebf2c80018bf6b757

The paged-scale pool now uses `(block, row_in_block)` rather than a flattened row index that could grow with the entire KV slab, and descriptor creation rejects unrepresentable TMA row spans instead of allowing silent coordinate wrap.

**Why it matters:** layout/index ranges are part of correctness. A faster kernel is irrelevant if large production geometries can silently index the wrong data.

**Candidate:** useful methodology precedent for `mojo-analyze`: size-boundary tests should deliberately exercise representable-limit edges instead of validating only small benchmark inputs.

### O04 — Sampling RNG is tied to requests instead of physical batch slots

**Sources:**
- https://github.com/modular/modular/commit/4d497bf7e3d24a80058540bf7182ef0ad6f8e7d9
- https://github.com/modular/modular/commit/dac6788e1bc6d1b3c47458d2bfe6e89217421f5a

MAX sampling and speculative-verdict randomness previously depended on batch-slot placement/shared graph RNG state. The fixes key random draws to the logical request so the same request/seed is not changed merely by colocating it in another physical slot.

**Why it matters:** determinism claims need to specify the identity used to seed random streams. “Same seed” is insufficient if scheduler placement leaks into the counter.

**Candidate:** for future stochastic Mojo workloads, record logical work-item identity and scheduling configuration separately and test schedule-invariant reproducibility.

## 2. Repository discoveries and deep dives

### R01 — `shivasankarka/hdf5-mojo`: scientific HDF5 interoperability

**Repository:** https://github.com/shivasankarka/hdf5-mojo  
**Domain:** scientific I/O / FFI  
**Evidence:** README inspected; source discovery, not a claim of a new Sep-16 release.

The library wraps the HDF5 C API with an h5py-shaped Mojo interface, supports datasets/groups/attributes, chunking, gzip/shuffle/Fletcher32 filters, hyperslabs, scalar datasets, and uses NuMojo arrays for N-D reads. It is explicit about missing advanced HDF5 features such as strings, compound types, MPI/parallel HDF5 and SWMR.

**Why interesting:** it exposes realistic FFI ownership, slicing and bulk-I/O boundaries rather than synthetic call overhead. A fair experiment would decompose HDF5 native I/O, FFI wrapper overhead and Mojo-side array materialization.

### R02 — `SergiuDeveloper/mojo-tensor`: explicit GPU autodiff framework

**Repository:** https://github.com/SergiuDeveloper/mojo-tensor  
**Domain:** GPU / ML systems  
**Evidence:** README inspected; documented requirement is an older 0.26.2-era Mojo dev build.

It provides dense layers, a computational graph, reverse-mode training flow, tiled GPU matrix multiplication, ReLU/MSE kernels and SGD updates.

**Why interesting:** this is a small enough training stack to study forward/backward kernel composition without inheriting a large framework. Its old toolchain pin is a compatibility risk and should be tested before performance work.

### R03 — `redhat-et/need-for-speed`: cross-language GPU-kernel benchmark harness

**Repository:** https://github.com/redhat-et/need-for-speed  
**Domain:** GPU benchmarking / methodology  
**Evidence:** README inspected.

The project compares Mojo tiled/naive GEMM, Triton and cuBLAS/PyTorch, with shared correctness tests and JSON benchmark output. Mojo uses async DRAM→SRAM copies and barriers; Triton uses autotuning/grouped program IDs.

**Why interesting:** it is a replication candidate precisely because implementations are not algorithmically identical. A useful `mojo-analyze` study would first normalize dtypes, warmup, synchronization, layouts and tuning budgets, then report the implementation differences instead of treating language labels as the only variable.

### R04 — `konjoai/vectro`: mixed Mojo/Rust/Python embedding compression

**Repository:** https://github.com/konjoai/vectro  
**Domain:** vector compression / SIMD  
**Evidence:** README inspected; throughput claims are author-reported.

Vectro combines optional Mojo SIMD kernels with Python/NumPy and Rust paths for INT8/NF4/PQ/binary quantization and ANN workflows. Its README also documents reproducibility controls such as coefficient-of-variation gates and environment provenance.

**Why interesting:** this is a useful example of a mixed-language system where “Mojo performance” must be scoped to a specific kernel path. Author claims such as multi-million vectors/sec or comparisons with FAISS are replication targets, not accepted results here.

### R05 — `bernaferrari/material-color-utilities-mojo`: color science with golden parity

**Repository:** https://github.com/bernaferrari/material-color-utilities-mojo  
**Domain:** image/color science / numerical correctness  
**Evidence:** repository README inspected through the public source page.

The project implements HCT/CAM16, tonal palettes, dynamic schemes, contrast, quantization and color-temperature relationships and checks behavior against extracted Material Color Utilities fixtures. It pins a specific 1.1 nightly rather than stable Mojo.

**Why interesting:** the golden-fixture approach is more valuable than a microbenchmark alone. A future test could compare one quantizer against the reference fixture suite first, then inspect SIMD/codegen only after parity passes.

### R06 — `conorbronsdon/mojo-tar`: pure-Mojo archive container work

**Repository:** https://github.com/conorbronsdon/mojo-tar  
**Domain:** serialization / file formats  
**Evidence:** README inspected through original repository page.

This project implements ustar/GNU/pax tar reading and writing in Mojo and intentionally leaves compression to separate libraries.

**Why interesting:** archive parsing creates a bounded binary-format workload with headers, checksums, padding and byte-exact output. A fair experiment could compare decode/encode separately and require byte-identical output to GNU/Python reference fixtures.

### R07 — `conorbronsdon/mojo-markdown`: spec-driven parser instead of throughput-first parser

**Repository:** https://github.com/conorbronsdon/mojo-markdown  
**Domain:** text parsing / conformance  
**Evidence:** README inspected through original repository page; its conformance percentage is an author claim.

The parser targets CommonMark and exposes both block parsing and HTML rendering. The project emphasizes conformance fixtures, including tricky delimiter/emphasis cases.

**Why interesting:** it reinforces that parser benchmarking needs a conformance gate. Throughput without the same accepted language is not apples-to-apples.

### R08 — `conorbronsdon/mojo-url`: Python-shaped URL parsing in pure Mojo

**Repository:** https://github.com/conorbronsdon/mojo-url  
**Domain:** protocol/string parsing  
**Evidence:** README inspected through original repository page.

It mirrors `urllib.parse`-style operations: parse, join, quote/unquote, query-pair parsing and encoding.

**Why interesting:** URL parsing is a compact workload with branch-heavy scanning and percent-encoding; it could become a parser benchmark independent of hash tables, provided a shared reference corpus and exact output contract are defined.

### R09 — `sstadick/mojopt`: reflection-driven CLI parsing

**Repository:** https://github.com/sstadick/mojopt  
**Domain:** compile-time reflection / developer tooling  
**Evidence:** README inspected; project labels itself active development.

`mojopt` derives CLI structure from Mojo structs, supports options, positional arguments and subcommands, and uses reflection to synthesize defaults/deserialization behavior.

**Why interesting:** unlike runtime parser benchmarks, this suggests measuring compile-time cost and generated-code size as CLI schemas scale. The useful question is not merely runtime argument parsing speed.

### R10 — `mojoto/morrow.mojo`: date/time semantics and formatting

**Repository:** https://github.com/mojoto/morrow.mojo  
**Domain:** date/time library  
**Evidence:** current repository README inspected.

Morrow provides parsing, formatting, fixed-offset zones, ISO-8601/POSIX handling, shifting/comparison and humanized date-time APIs.

**Why interesting:** date/time code is correctness-heavy. A benchmark should start from edge-case fixtures—leap years, offsets, timestamp boundaries—before measuring parse/format throughput.

### R11 — `Lightbug-HQ/lightbug_http`: an archived systems-project baseline

**Repository:** https://github.com/Lightbug-HQ/lightbug_http  
**Domain:** systems/networking  
**Evidence:** repository page inspected; repository explicitly archived 2026-05-12.

Lightbug was a pure-Mojo HTTP/1.1 framework with typed request/response/server components, but the repository is now read-only and directs users toward newer libraries.

**Why interesting:** this is included as ecosystem archaeology, not current activity. Archived code can still supply protocol/parsing workloads, but current compatibility and maintenance status must be re-established before using it as a benchmark dependency.

### R12 — `dorjeduck/llm.mojo`: Mojo port of an earlier `llm.c`

**Repository:** https://github.com/dorjeduck/llm.mojo  
**Domain:** ML training / CPU kernels  
**Evidence:** repository README inspected through original source page.

The project ports an earlier `llm.c` GPT-2 training codebase and now pins Mojo 1.0 / MAX 26.5. Its own README notes that current upstream `llm.c` has newer CPU matmul optimizations.

**Why interesting:** that disclosure is exactly why historical ports should not be used for headline language comparisons without matching upstream algorithm revisions. A useful experiment would normalize one matmul implementation level before timing.

The package guide documents source packages, `.mojopkg` creation and deferred architecture-specific elaboration. This is useful context when deciding whether a benchmark artifact is portable source IR, compiler-version-coupled precompiled content, or a final target binary.

### A04 — System requirements and GPU compatibility tiers

**Source:** https://docs.modular.com/mojo/requirements/

The docs distinguish continuously tested GPUs from merely known-compatible hardware. Radar and benchmark reports should preserve that distinction rather than treating “supported” as one uniform evidence level.

### A05 — External ORC-host accelerator compilation request (#6936)

**Source:** https://github.com/modular/modular/issues/6936  
**Date:** 2026-08-20

The xmojo authors want a supported boundary for persistent in-process KGEN/ORC compilation with accelerator backends. The issue exposes an architectural boundary between open host compilation and accelerator code generation that matters for notebook/JIT tooling.

### A06 — Mojo compiler virtual-address-space pressure in constrained CI (#6433)

**Source:** https://github.com/modular/modular/issues/6433  
**Date:** 2026-04-21

The issue documented very large compiler virtual address reservations and nondeterministic failures when multiple compiler processes ran on memory-constrained CI. Even if the exact numbers drift, the durable lesson is to record compiler concurrency and memory limits when CI compile failures appear random.

### A07 — Metal empty-kernel enqueue overhead investigation (#6566)

**Source:** https://github.com/modular/modular/issues/6566  
**Date:** 2026-05-18

This issue isolates launch overhead with an empty kernel rather than measuring a full workload. That methodology is useful: before comparing GPU kernels, decompose fixed dispatch cost from resident computation and transfer.

### A08 — “Mojo: A Promising Tool for Scalable Financial AI Efficiency”

**Source:** https://arxiv.org/abs/2606.16059  
**Published:** 2026-06-14

The article discusses deterministic kernels and financial workloads and mixes directly measured CPU results with explicitly projected larger-scale GPU results.

**Why read it:** it is a reminder to separate measured from projected results in a single source. Any finance-style Monte Carlo or reduction benchmark should specify reproducibility/rounding contracts before speed claims.

## 5. Research candidates

1. **Category-D parser-only vs parser+hash decomposition** — strongest existing canonical next step. Preserve file read, delimiter scan and numeric parse; omit FNV; run parser-only and parse+hash in the same interleaved x86_64/arm64 job with equal checksums. This isolates hashing from scanning/parsing after yesterday showed the arm64 gap already exists before the table.
2. **Shared Mojo package-cache concurrency stress** — verify the Sep-16 atomic cache fix across pinned compiler revisions if a source/nightly build can be reproduced safely.
3. **HDF5 boundary decomposition** — same HDF5 dataset and native library; separate native read, FFI wrapper and Mojo NDArray materialization.
4. **URL/CommonMark parser conformance-before-throughput** — construct a fixed reference corpus and exact output contract before comparing parser speed.
5. **GPU launch/compute decomposition** — use empty/minimal kernels to quantify fixed launch cost before any Mojo-vs-other-GPU-language comparison.
