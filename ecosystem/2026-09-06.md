## Systems / networking: `mojo-http` moves blocking-thread handoff onto in-memory rings

Repository: https://github.com/codetalcott/mojo-http

### Ring handoff separates payload transport from wake transport

Commit `da4735a` changes the `--blocking-threads` worker-pool handoff so ordinary jobs/completions ride in-memory rings while socketpairs carry wakes and exceptional payloads. This is technically different from merely replacing one queue implementation with another: it splits **data ownership** from **scheduling notification**.

Why interesting: once a wake becomes a credit rather than the job itself, correctness depends on a precise invariant between queued work and parked workers. That makes queue throughput, wake frequency, and lost-wake behavior separable dimensions instead of one opaque IPC cost.

Potential `mojo-analyze` experiment: if a concurrency/messaging category is eventually added, measure payload transfer and notification overhead independently; do not benchmark only an end-to-end thread-pool request rate.

Sources:
- https://github.com/codetalcott/mojo-http/commit/da4735a29abcea1e2a4d6c83a3b34fcd76fb557d
- https://github.com/codetalcott/mojo-http/commit/043ac1df500843575c51561b69a883c228751e22

### A reproducible lost-wake race appeared after the ring change

Commit `b9a152c` records a useful failure sequence. A thread woken for one job could poll its socket before returning to the ring and consume a wake intended for a second parked thread. The result was two jobs but only one active worker; the delayed job surfaced only when another slow worker later returned to the ring. The project reports reproducing the failure in 2/10 Linux rounds with the ring, 0/10 with the ring disabled, and 0/20 after adding a chain-wake rule: a thread that takes a job and leaves work queued wakes a parked sibling.

Why interesting: this is a concrete concurrency lesson about **wake ownership not being equivalent to work ownership**. A notification channel can be lossy at the protocol level even when the underlying socket/datagram delivery is reliable, because the wrong consumer can legally consume the notification.

Potential experiment: build a deterministic microbenchmark around N queued jobs / M parked workers and record both latency tail and stranded-work count. Treat `jobs remain queued while workers remain parked` as a correctness failure, not merely a slow trial.

Source:
- https://github.com/codetalcott/mojo-http/commit/b9a152c2682c8b5af6b15c044c0b7c5e58518f9a

### Streaming completion needed an ordering barrier, not another event

Commit `f56aec6` fixes a related ordering failure: completion was visible before a prior hold/bus frame had been drained, allowing the loop to finish/close a streaming slot before the earlier logical event was processed. The fix drains relevant channels before finalizing a streaming head/101 completion.

Why interesting: event-loop correctness can depend on causal ordering between two channels even when each channel is individually FIFO. A benchmark for async/network systems should include protocol-state invariants, not just throughput and latency.

Source:
- https://github.com/codetalcott/mojo-http/commit/f56aec6143b16a15addcd47ac6d9c3a4a113e874

### Spin interval was measured rather than guessed

Commit `609d240` reports that a 10 µs spin interval retained the throughput of a 30 µs setting while returning about a tenth of a CPU core. This is a small result, but methodologically useful: busy-wait tuning needs throughput **and CPU cost** in the objective, otherwise a throughput-only benchmark can reward unnecessary spinning.

Source:
- https://github.com/codetalcott/mojo-http/commit/609d2403f6344a6d7849dea17b93977265e226ce

## Benchmark provenance: `mojo-http` gates stale benchmark tables

Merge `ef489c9` updates benchmark provenance so published tables are tied to current artifacts/version shape rather than silently surviving code changes. This follows the same general direction as `mojo-analyze`'s checksum and controlled-environment rules: a number without a precise producing artifact is not durable evidence.

Why interesting for `mojo-analyze`: benchmark result provenance should eventually include executable/toolchain identity in a machine-readable form, not only hardware and source commit in prose.

Potential infrastructure experiment: add a non-invasive provenance record containing source SHA, Mojo version, Rust/C compiler versions, OS/arch and benchmark parameter hash beside future result snapshots.

## Graphics / GPU / FFI: `wgpu-mojo` publishes 0.2.1 as its first one-command package

Repository: https://github.com/Hundo1018/wgpu-mojo

Commit `2dc4f7f` releases `wgpu-mojo` 0.2.1 as the first version intended to be installed directly from a channel with one `pixi add`. The project explicitly keeps 0.3.0 for an API redesign; 0.2.1 is packaging/reproducibility work rather than an API performance change.

Why interesting: this lowers the friction for reproducible WebGPU/compute experiments in Mojo. For `mojo-analyze`, the important change is not a new graphics feature but that an external GPU substrate can now be pinned and installed more predictably in CI or a benchmark environment.

The accompanying documentation also calls out a strict `wgpu-native` ABI pin: a seemingly compatible patch version can silently misread descriptors. That is a valuable FFI constraint—semantic version compatibility at the package level does not imply ABI compatibility at a native boundary.

Sources:
- https://github.com/Hundo1018/wgpu-mojo/commit/2dc4f7f6dece61a2aafa60b3dd22b48b13a335d9
- https://github.com/Hundo1018/wgpu-mojo/commit/3f1dfc34fa0dcbac78d0cb0b164c1dc121eae565

### Release artifact selection itself caused a provenance bug

Commit `05ede15` fixes the 0.2.1 GitHub Release accidentally attaching four `.conda` files instead of the two packages built for that release. Because the recipe cloned the repository into the build tree, a broad recursive artifact glob also matched stale committed packages. The fix both narrows the upload glob and removes committed `.conda` artifacts.

Why interesting: build-tree contents are not equivalent to build outputs. Artifact upload rules should positively select the producer's output directory, not recursively collect matching extensions from a workspace.

Source:
- https://github.com/Hundo1018/wgpu-mojo/commit/05ede15eaba6360fa2661a73f6f3e3b08151e9cf

Potential `mojo-analyze` use: once a WebGPU experiment is justified, separate timings into pipeline creation, host↔device transfer, resident-buffer dispatch, and readback. The now-installable package makes that experiment easier to reproduce, but no new GPU performance claim is inferred from the release itself.

## What changed from 2026-09-05

1. **Official tree remains unchanged** — still Mojo `1.1.0.dev2026090305` / MAX `26.6.0.dev2026090305`.
2. **`mojo-http` changed its blocking-thread handoff architecture** — payloads moved to in-memory rings while sockets became wake channels.
3. **That architecture immediately exposed two protocol-ordering bugs** — a wake could be consumed by the wrong worker, and completion could become visible before a logically earlier bus frame was drained.
4. **Busy-wait tuning gained a CPU-cost dimension** — 10 µs retained measured throughput while using less CPU than 30 µs in the reported test.
5. **`wgpu-mojo` became materially easier to reproduce** — 0.2.1 is its first one-command packaged release, with explicit ABI pinning and a release-artifact provenance fix.

## Research candidates

1. **Rust Category C hasher-cost experiment** — the canonical repo still has an unresolved fair-comparison question: keep Category C's owned `Vec[u8]` token keys and algorithm unchanged, swapping only Rust's default `HashMap` hasher for the already validated incremental FNV-1a implementation used by the Category D experiment. This isolates hasher cost without conflating key ownership.
2. **Wake-credit correctness microbenchmark** — N queued jobs / M parked workers; record stranded work, tail latency and wake count, not only aggregate throughput.
3. **Benchmark provenance sidecar** — source SHA + toolchain/compiler versions + OS/arch + parameter hash beside result snapshots.
4. **WebGPU phase decomposition** — with `wgpu-mojo` 0.2.1 pinned, separately measure pipeline creation, upload, resident dispatch and readback for one deterministic compute kernel.
5. **Artifact-selection regression fixture** — verify a release upload rule cannot collect stale package-shaped files from nested build/work directories.
