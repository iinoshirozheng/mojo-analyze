### O02 — GPU top-k now initializes the unwritten tail when stage 2 exhausts candidates

**Lane:** recent correctness fix — 2026-09-23.  
**Source:** https://github.com/modular/modular/commit/1c93ea4c994b5f25d97cdd9be154ea3efc86ebea

The multi-block top-k path could stop after encountering its dead sentinel without writing all output positions when fewer than `k` valid candidates remained. Stale device memory could then be interpreted as plausible indices; the commit ties this to an illegal-address failure in a DeepSeek-V4 path. The fix writes sentinel values and `-1` indices through the remaining tail and checks the GPU implementation against a CPU reference/golden path.

**Why it matters technically:** partially initialized outputs can turn a local selection edge case into a downstream memory-safety failure. A speed benchmark that validates only common full-k rows would miss it.

**Research angle:** selection benchmarks should include sparse/underfilled rows and validate the entire output buffer, including invalid-tail semantics, before timing.

### O03 — `hlcf.if` / `hlcf.comptime.if` keep explicit `elif` regions deeper into the compiler

**Lane:** recent compiler/control-flow work — 2026-09-23.  
**Sources:**  
- https://github.com/modular/modular/commit/9e1d8ae17a4956dd4688e6a257c764dd89c9747f  
- https://github.com/modular/modular/commit/44193f1379f605060f80d670f7c56b3bbc5db52a  
- https://github.com/modular/modular/commit/aa7aba6a99307a19c82bce8acc297ea837b7eca5

The compiler is generalizing explicit `elif` regions rather than immediately nesting them into repeated `else { if ... }` forms. Canonicalizers are being updated to preserve and simplify the shallower representation.

**Why it matters technically:** source-equivalent control flow can create very different IR depth and compile-time work. This is primarily a compiler-scalability/code-structure signal, not a runtime-performance claim.

**Research angle:** a future compile-only probe could scale long `elif` chains across pinned revisions and compare IR depth/pass time while keeping generated runtime behavior identical.

### O04 — DeepSeek-V4 architecture lands with sparse/cache-specific state, then moves onto paged KV leaves

**Lane:** recent MAX/model-runtime development — 2026-09-23.  
**Sources:**  
- https://github.com/modular/modular/commit/c17214b06beb260b8118c2997af6e08979236d96  
- https://github.com/modular/modular/commit/b9d48ef75535e65494eabbe8f4cae2797a1bf7ac

MAX adds a DeepSeek-V4-Flash architecture with compressed/sparse attention, an attention sink, lightning indexer, mHC and MoE-specific paths, then follows with paged KV-cache leaves sharing a token page table across the sparse-attention state. The initial implementation is checked against vLLM-derived golden behavior on a minimized checkpoint.

**Why it matters technically:** logical token position, sliding-window state, compressed entries and physical cache pages are distinct indexing domains. Reusing one page table does not make those domains semantically interchangeable.

**Research angle:** any cache benchmark should carry shape-aware correctness fixtures and report logical reuse depth separately from physical page/slot layout.

## 2. Repository discoveries / deep dives — 12

### R01 — `josiahls/mav`: low-level FFmpeg 8 bindings for Mojo

**Repository:** https://github.com/josiahls/mav  
**Domain:** audio/video / C FFI  
**Lane:** newly discovered existing project; README labels the library alpha.

MAV binds FFmpeg 8.x (`avcodec`, `avformat`, `swscale`, `swresample`, etc.) into Mojo and deliberately stays low-level rather than hiding FFmpeg's native model behind a new high-level abstraction.

**Why it matters:** media workloads mix codec compute, allocation, format conversion, filesystem I/O and FFI. Treating total decode time as a “Mojo codec” number would misattribute most of the work.

**Experiment angle:** validate one frame/audio-buffer metadata and byte output against a small C/FFmpeg oracle, then measure fixed FFI/control overhead separately from codec execution.

### R02 — `lsh/shimmer`: Mojo as a creative-coding/shading language over OpenGL textures

**Repository:** https://github.com/lsh/shimmer  
**Domain:** graphics / rendering / creative coding  
**Lane:** newly discovered experimental project.

Shimmer is inspired by nannou and experiments with cross-platform rendering to OpenGL textures while expressing the shading/creative-coding layer in Mojo. The repository uses Bazel and is intentionally exploratory.

**Why it matters:** it is a graphics path distinct from native accelerator kernels and from large engine bindings: Mojo computes/expresses a render surface while OpenGL owns presentation.

**Experiment angle:** isolate a deterministic pixel kernel into an off-screen buffer with a byte/image digest; keep swap/vsync/presentation outside the measured region.

### R03 — `mrvoll98/trellis2-mojo`: end-to-end native image-to-3D inference on Apple Silicon

**Repository:** https://github.com/mrvoll98/trellis2-mojo  
**Domain:** ML systems / Metal GPU / geometry  
**Lane:** newly discovered current project; stable Mojo 1.0 + minimal MAX Core 26.5 are pinned.

The port covers image preprocessing, DINO conditioning, deterministic noise, diffusion-transformer sampling, VAE decode, mesh extraction/remeshing and GLB export without a PyTorch tensor bridge. It carries CPU/GPU regression checks and documents f16 borderline-voxel differences rather than claiming exact mesh identity. Published M4 Pro timing improvements are author-reported.

**Why it matters:** this is a rare large Mojo application where numerical tolerance, device residency, I/O and geometry post-processing all have explicit boundaries.

**Experiment angle:** reproduce one small attention/GEMM or mesh-extraction stage with a numerical/structural oracle before using end-to-end minutes as language evidence.

### R04 — `TylerHillery/write-your-own-vm`: LC-3 virtual machine port

**Repository:** https://github.com/TylerHillery/write-your-own-vm  
**Original showcase:** https://forum.modular.com/t/lc-3-vm-mojo-implementation/3327  
**Domain:** systems / virtual machines / terminal I/O  
**Lane:** newly discovered existing project.

The project ports the classic small LC-3 VM to Mojo. Its development history is technically useful: terminal input initially used Python interoperability, then moved to native termios code after community FFI guidance.

**Why it matters:** it exposes a realistic migration boundary where the core interpreter loop was straightforward but operating-system interaction required ABI work.

**Experiment angle:** compare instruction-dispatch behavior against the reference C VM on the same object program and final machine state; benchmark the core loop separately from terminal polling.

### R05 — `conorbronsdon/mojo-feed`: RSS, Atom and JSON Feed parsing in pure Mojo

**Repository:** https://github.com/conorbronsdon/mojo-feed  
**Domain:** parsing / XML+JSON / compatibility  
**Lane:** newly profiled repository identity; sibling parser projects have appeared in earlier briefs.

`mojo-feed` combines a non-validating XML pull parser with RSS/Atom mapping and a JSON Feed path. Its pull-parser work later became a foundation for the author's general XML package.

**Why it matters:** feed parsing mixes tokenization, namespace/date handling and domain materialization. It is more realistic than a delimiter microbenchmark but still supports reference-fixture comparison.

**Experiment angle:** use a frozen RSS/Atom corpus and compare pull-tokenization versus feed-object construction, with normalized domain digests before timing.

### R06 — `DataBooth/py-run-mojo`: three Python↔Mojo execution boundaries

**Repository:** https://github.com/databooth/py-run-mojo  
**Package:** https://pypi.org/project/py-run-mojo/  
**Domain:** Python interoperability / notebooks / build caching  
**Lane:** newly profiled existing project.

The project exposes a cached subprocess/decorator route and compiled extension-module route for invoking Mojo from Python. Its documentation explicitly distinguishes first compile, cached execution, and direct extension calls; published speedup numbers are author-reported.

**Why it matters:** “calling Mojo from Python” is not one cost model. Process launch, compilation/cache lookup, serialization and in-process FFI have radically different fixed costs.

**Experiment angle:** a no-op/scalar/small-array size sweep can locate each boundary's fixed overhead while preserving exact values and excluding the workload itself.

### R07 — `exergy-connect/mojo-js`: Mojo-flavored source to JavaScript transpiler experiment

The project explores a custom lexer/AST/transpiler that maps a Mojo-shaped language subset to JavaScript, with a small CI-tested corpus. Its goal is conceptual browser/distributed execution rather than compatibility with the full current Mojo compiler.

**Why it matters:** generated-source tools should be judged first on semantic coverage and diagnostics, not on throughput or source-size headlines.

**Experiment angle:** freeze a supported-language corpus and compare generated JavaScript behavior against a direct reference; count unsupported constructs explicitly before measuring transpilation cost.

### R09 — `thomas-gale/mo3d`: ECS-oriented 3D/ray-tracing experiment

**Domain:** graphics / ECS / ray tracing / simulation

`mo3d` explores a Mojo-native ECS, ray/path tracing, SIMD-aware vector/matrix storage and SDL-backed display. Historical notes distinguish compute time from texture-copy/redraw time and document a BVH that was initially slower on small scenes.

### R10 — `leo-gan/GLD.SerializerBenchmark`: multi-language serializer methodology with a Mojo lane

**Repository:** https://github.com/leo-gan/GLD.SerializerBenchmark

### R11 — `ulmentflam/llm.mojo`: GPT-2 training with CUDA and Metal kernels

**Repository:** https://github.com/ulmentflam/llm.mojo

## 5. Ranked research candidates

1. **Category-D arm64 scanner mode / CPU-affinity diagnostic** — yesterday reproduced two stable timing modes in Mojo 1.2 checked-`Span` scanning while pointer and C controls stayed stable. Re-run the *same binary/source/corpus* with unpinned versus single-CPU-affined processes, raw samples and the same checksum to test whether scheduler/core placement is sufficient to explain mode occupancy. This is the strongest unresolved canonical hypothesis and does not modify the benchmark implementation.
2. **GLD serializer call-path replication** — choose one Mojo JSON/CBOR row, preserve its prepare/timed/fidelity boundary and independently reproduce before comparing parser designs.
3. **`trellis2-mojo` stage oracle** — isolate one small GPU attention/GEMM or mesh-extraction stage with a CPU/numerical reference and explicit transfer/residency timing.
4. **MAV C-ABI oracle** — verify FFmpeg struct/value behavior against a tiny C program, then measure fixed FFI/control overhead separately from codec work.
5. **`mo3d` BVH crossover** — deterministic rays/scenes, exact hit digest, sweep primitive count to find where BVH construction/traversal beats linear traversal.
