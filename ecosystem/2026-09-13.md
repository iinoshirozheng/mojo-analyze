### O02. KDA CPU reference now uses embedded FP64 golden outputs

**Freshness:** recent correctness-methodology change, 2026-09-13.  
**Source:** https://github.com/modular/modular/commit/163419a1a6d63318ccf2e463d30743c6dbc213d4

KDA tests now compare the CPU reference against embedded FP64 golden outputs with a much tighter RMSE-ratio tolerance than the GPU-oriented test path; the same change also checks two supported K/V layout orders against one another.

**Why it matters:** a “reference implementation” is stronger when it is itself checked against an independent oracle. For future numerical/GPU work in `mojo-analyze`, a CPU comparator should not automatically be treated as ground truth merely because it runs on CPU.

**Experiment angle:** preserve an external or higher-precision oracle for one small numerical kernel, then use the validated CPU implementation as the cheaper repeated comparator.

### O03. Native prefill fuses expert-parallel dispatch with MegaFFN layout production

**Freshness:** recent MAX/GPU implementation change, 2026-09-13.  
**Source:** https://github.com/modular/modular/commit/0317c28320672b07bef28a93292f020f82aaa30b

The new path fuses expert-parallel dispatch with MegaFFN-oriented data layout instead of materializing an intermediate then running a separate compaction/rearrangement pass. The commit describes a Mojo implementation inspired by DeepGEMM-style push/pull work decomposition; EP combine is explicitly outside this change.

**Why it matters:** this is an algorithm/data-movement change, not merely instruction tuning. Eliminating an intermediate layout transform can matter more than optimizing an isolated compute kernel.

**Experiment angle:** for a future staged pipeline, measure “produce directly into consumer layout” versus “produce + transform,” accounting separately for bytes moved and kernel launches.

### O04. KV cache can decouple cached entries per page from token page size

**Freshness:** recent runtime/data-layout change, 2026-09-13.  
**Source:** https://github.com/modular/modular/commit/7f40577874f576d68f8dd94fa0b190f0ba4cec0a

KV cache pages can now use `slots_per_page` independently from token page size for architectures that compress several tokens into one cached entry. Existing behavior remains the default, and the slot count must divide the page size; page-table/prefix-cache semantics remain token-based while buffer layout changes.

**Why it matters:** logical indexing units and physical storage units can diverge. Benchmarks involving compressed/cached representations must state both rather than treating “page size” as a single sufficient parameter.

## B. Repository discoveries — 12

### R01. `egor-fedorov/safetensors` — native Safetensors with lifetime-checked mmap views

**Domain:** model-weight formats / zero-copy I/O / ownership.  
**Freshness:** recent community release; Safetensors.mojo 0.7.0 was showcased Sep 9.  
**Repository:** https://github.com/egor-fedorov/safetensors  
**Author showcase:** https://forum.modular.com/t/safetensors-mojo-0-7-0-safetensors-in-pure-mojo/3479

The library reads/writes single-file and sharded Safetensors without a Python/tensor-runtime dependency. The author describes memory-mapped typed views whose lifetimes are tied to the mapping owner through Mojo origins, deterministic atomic writing, checked arithmetic, duplicate-key/index validation, fuzzing, differential tests against the official implementation, and compile-fail lifetime tests. CI targets Mojo 1.0.0 on Linux x86-64/ARM64 and macOS ARM64.

**Why interesting:** it combines file-format correctness, mmap lifetime safety and zero-copy access. The author explicitly reports Rust leading the benchmark, which is more useful than a marketing-only speed claim.

**Research angle:** split mmap/open/validation cost from repeated zero-copy tensor access and compare byte-identical metadata/data views.

### R02. `nsalerni/protomojo` — Protocol Buffers runtime + `protoc` plugin

**Domain:** serialization / code generation / protocol interoperability.  
**Freshness:** current package discovery; the nightly package catalog lists Mojo `>=1.0.0,<1.1.0`.  
**Repository:** https://github.com/nsalerni/protomojo

`protomojo` provides protobuf wire/runtime support plus generated Mojo types. It is also one component of a larger pure-Mojo gRPC stack whose author reports protobuf conformance and gRPC cross-language interoperability against external suites rather than self-only tests.

**Why interesting:** generated serialization code gives a strong reference contract: encode/decode bytes can be compared exactly with mature implementations.

**Research angle:** one fixed schema, encode/decode across message sizes, exact byte/field equality, with code-generation time kept separate from runtime serialization.

### R03. `ethqnol/polars-mojo` — Polars bindings through the Arrow C Data Interface

**Domain:** dataframe / Arrow / zero-copy interop.  
**Freshness:** newly surfaced in the current/nightly package catalog; targets Mojo 1.0.0.  
**Repository:** https://github.com/ethqnol/polars-mojo

The package exposes Polars to Mojo through Arrow-compatible interchange rather than rebuilding a dataframe engine in Mojo.

**Why interesting:** it is a useful attribution boundary. If computation is performed by Polars, end-to-end speed is not “Mojo dataframe performance”; the Mojo-specific question is conversion, ownership, schema, and crossing cost.

**Research angle:** sweep record-batch size to find where Arrow/FFI boundary cost amortizes, checking schema/null/value parity.

### R04. `caspbian/mojogp` — GPU-accelerated Gaussian Processes with packaged accelerator engines

**Domain:** scientific ML / GPU kernels / Python integration.  
**Freshness:** package `0.26.7.0` was published to modular-community in early September; package metadata still pins MAX 26.4 and Mojo 1.0.0b2.  
**Repository:** https://github.com/caspbian/mojogp  
**Package:** https://prefix.dev/channels/modular-community/packages/mojogp

MojoGP packages Gaussian-process acceleration with Python scientific dependencies and has separately published prebuilt accelerator artifacts for several CUDA architectures.

**Why interesting:** the version split exposes an important deployment reality: application package version, Mojo/MAX version, Python ABI, and GPU architecture are all independent provenance fields.

**Research angle:** isolate one covariance/kernel operation before attempting whole-GP training, and distinguish prebuilt-engine startup/dispatch from kernel time.

### R05. `sstadick/hat` — Cargo-like project workflow on top of Pixi

**Domain:** build tooling / packaging / stable-nightly workflow.  
**Freshness:** updated for Mojo 1.0 on Aug 18.  
**Repository:** https://github.com/sstadick/hat  
**1.0 showcase:** https://forum.modular.com/t/hat-support-for-mojo-1-0/3421

Hat wraps Pixi with `new`, `build`, `test`, stable/nightly scaffolding and current `.mojoc`/`precompile` behavior.

**Why interesting:** it addresses compiler/package churn operationally rather than inside application code. Its explicit stable/nightly project modes mirror `mojo-analyze`'s canonical-versus-advisory toolchain separation.

**Research angle:** not a runtime benchmark. Measure cold/incremental build orchestration only if build-system overhead becomes material, while keeping compiler work and wrapper work separate.

### R06. `sstadick/mojopt` — reflection-driven struct-to-CLI parsing

**Domain:** metaprogramming / CLI tooling.  
**Freshness:** existing project updated for Mojo 1.0; package catalog pins Mojo 1.0.0.  
**Repository:** https://github.com/sstadick/mojopt  
**Design showcase:** https://forum.modular.com/t/mojopt-a-structopt-like-cli-option-parser/2879

Mojopt derives command-line handling from struct definitions and reflection instead of manually building the option graph.

**Why interesting:** it offers a clean compile-time work-placement question: generated/derived structure may reduce runtime boilerplate while increasing compilation work or binary size.

**Research angle:** equivalent hand-built versus reflected CLI schema; compare semantics first, then compile time/code size and parse latency separately.

### R07. `martinvuyk/mojo-datetime` — calendars, time zones and leap-second-aware date/time

**Domain:** date/time / correctness-heavy standard-library extension.  
**Freshness:** version 0.1.3 was announced Jun 29 after major addition/subtraction speedups; current compatibility must be rechecked because the author documents use of a private stdlib wall-clock method.  
**Repository:** https://github.com/martinvuyk/mojo-datetime  
**Showcase:** https://forum.modular.com/t/mojo-datetime-a-flexible-mojo-datetime-library-implementation/3015

The project implements customizable calendars/time zones, epoch conversions, leap behavior, parsing/formatting and arithmetic in native Mojo.

**Why interesting:** date arithmetic is dominated by correctness edge cases; the author explicitly warns that one `now()` dependency is private/unstable.

**Research angle:** benchmark large time-delta arithmetic only after cross-checking boundary cases against an independent date library and separating wall-clock acquisition from calendar math.

### R08. `thecsguy/grpc-mojo` family — external conformance as the protocol oracle

**Domain:** networking / gRPC / HTTP2 / protobuf.  
**Freshness:** public showcase Aug 20, 2026.  
**Showcase:** https://forum.modular.com/t/grpc-mojo-grpc-implemented-in-pure-mojo-verified-against-grpcio/3428

The stack is split across `mojo-net`, `protomojo`, `mojo-http2`, and `grpc-mojo`. The author reports testing against **external** references: grpcio in both directions, h2spec, and Google's protobuf conformance suite.

**Why interesting:** protocol software should not grade its own homework. External conformance suites are more durable evidence than a large internal test count.

**Research angle:** if networking enters `mojo-analyze`, begin with one byte-exact codec/framing primitive and external oracle before requests/sec.

### R09. `mojoto/morrow` — human-friendly date/time utilities on Mojo 1.0

**Domain:** date/time / API ergonomics.  
**Freshness:** new discovery in this radar; current package catalog lists `mojo-compiler=1.0.0`.  
**Repository:** https://github.com/mojoto/morrow

Morrow focuses on managing, formatting and transforming dates/times/timestamps. It is a useful contrast to the more configurable `mojo-datetime` design.

**Why interesting:** two libraries in the same domain make API/design tradeoffs visible without turning package popularity into a benchmark.

**Research angle:** common parse/format/offset fixture corpus could compare semantic coverage and allocation/codegen only after matching supported behavior.

### R10. `Ryul0rd/vulkan-mojo` — generated Vulkan bindings

**Domain:** graphics / low-level GPU API / FFI.  
**Freshness:** new discovery; community catalog currently records an older MAX 25.6 requirement.  
**Repository:** https://github.com/Ryul0rd/vulkan-mojo

This project generates Mojo bindings for Vulkan rather than using Mojo's native accelerator stack or WebGPU.

**Why interesting:** it provides a third graphics path alongside native Mojo GPU and `wgpu-mojo`, but the older toolchain pin is a material compatibility caveat.

**Research angle:** first validate representative Vulkan struct layouts/constants and one headless compute path on a compatible pinned toolchain; do not compare graphics throughput before ABI correctness.

### R11. `hylkedonker/bridge` — Python↔Mojo object conversion

**Domain:** Python interoperability / object conversion.  
**Freshness:** new discovery; current package catalog still records MAX 25.4, so modern-toolchain compatibility is unverified.  
**Repository:** https://github.com/hylkedonker/bridge

Bridge's explicit purpose is converting Python objects to Mojo representations and back.

**Why interesting:** this is exactly the boundary that can dominate a “fast Mojo function called from Python” when payloads are small or nested.

**Research angle:** no-op/scalar/small-array/large-array round trips with correctness checks, separating conversion from the foreign function's actual work.

### R12. `moseschmiedel/mogo_tester` — mixed-language Mojo test orchestration

**Domain:** test tooling / compiler orchestration.  
**Freshness:** Go module v2.2.0 was published Jun 5, 2026.  
**Repository:** https://github.com/moseschmiedel/mogo_tester  
**README mirror:** https://pkg.go.dev/github.com/moseschmiedel/mogo_tester/v2

The Go-based runner discovers top-level Mojo tests, compiles each with `mojo build`, executes binaries with pseudo-TTY stdout/stderr, supports bounded parallelism and optional ASan, and distinguishes compile/run results.

**Why interesting:** mixed-language developer tooling is part of the Mojo ecosystem even when GitHub's primary language is not Mojo; a `language:Mojo` query misses it.

**Research angle:** compare sequential versus bounded-parallel compile-test orchestration while preserving per-file outcomes; this measures workflow throughput, not compiler speed per test.

## C. Technical reading — 8 selections

### A01. Pattern matching + Enum proposals

**Source:** https://forum.modular.com/t/pattern-matching-enum-proposals/3473  
**Published:** 2026-09-07; discussion still active through Sep 12.

The proposal discussion exposes representation/desugaring, exhaustiveness and ergonomics questions around future sum types. It is design-stage material, not current stable syntax; do not write benchmarks against a proposal as if shipped.

### A02. Writing DuckDB extensions in Mojo

**Source:** https://forum.modular.com/t/writing-duckdb-extensions-in-mojo/3488  
**Published:** 2026-09-11.

The author integrates Mojo audio-feature computation as DuckDB SQL functions and reports thread-safe stateless C-ABI behavior plus multi-core scaling. Those figures are author measurements. The useful idea is decomposition: DuckDB scheduling, C-ABI calls and Mojo compute are different layers.

### A03. Float64 `std.math` accuracy versus system libm

**Source:** https://forum.modular.com/t/float64-accuracy-of-std-math-on-cpu-measured-against-the-system-libm-mojo-1-0-0/3460  
**Published:** 2026-09-01/02.

A reproducible first section compares Mojo 1.0 Float64 functions to glibc `libm`, with larger AI-generated survey results clearly labeled as not independently reproduced. Especially useful are the caveats: libm is not a correctly-rounded oracle, and result-class/subnormal failures are different from ordinary ULP drift.

**Learning angle:** numerical benchmarks need an error contract and a reference hierarchy, not “checksum equal” when floating-point semantics legitimately differ.

### A04. Writing multithreaded code today

**Source:** https://forum.modular.com/t/writing-multithreaded-code-today/3463  
**Published:** 2026-09-02; origins-based refinement Sep 3.

A practical exploration of Mojo 1.0 multithreading, revised to lean more heavily on Origins after community feedback.

**Learning angle:** concurrency examples should be treated as ownership/lifetime experiments first; throughput comes after race/lifetime semantics are established.

### A05. Mojo FP16 GEMM on consumer RDNA3 versus hipBLASLt

**Source:** https://forum.modular.com/t/a-mojo-fp16-gemm-that-beats-hipblaslt-on-a-consumer-rdna3-card-rx-7900-xtx-with-the-receipts/3471  
**Published:** 2026-09-06.

The author reports a WMMA Mojo kernel beating hipBLASLt on selected square sizes on an RX 7900 XTX and provides a matched-box methodology. Treat the table as a replication target, not a portable Mojo superiority claim.

**Learning angle:** fixed hardware/library versions and a shape sweep are essential; a single matrix size can conceal crossover points.

### A06. gRPC in pure Mojo, verified against grpcio/h2spec/protobuf conformance

**Source:** https://forum.modular.com/t/grpc-mojo-grpc-implemented-in-pure-mojo-verified-against-grpcio/3428  
**Published:** 2026-08-20.

This is valuable as a testing-methodology article even beyond the repo profile: use independent standards suites and opposite-direction cross-language interop, not only unit tests written by the same implementation author.

### A07. What should a future Mojo package manager support?

**Source:** https://forum.modular.com/t/open-question-what-would-you-like-to-see-from-a-mojo-package-manager/2799  
**Published:** 2026-03 onward.

The discussion spans pure-Mojo projects, Python acceleration, transitive users, GPU/kernel developers, air-gapped systems, large libraries, build-time codegen, native dependencies, hardware metadata and supply-chain signing.

**Learning angle:** Mojo packaging has unusually polyglot/hardware-sensitive requirements. Reproducible benchmark environments benefit from making compiler, native library, GPU/driver and build-tool constraints machine-readable.

### A08. `mogo_tester` design: compile each Mojo test and preserve terminal behavior

**Source:** https://pkg.go.dev/github.com/moseschmiedel/mogo_tester/v2  
**Published:** v2.2.0, 2026-06-05.

The tool's README is a useful mixed-language workflow design note: pseudo-TTY-backed execution preserves terminal-aware output, parallel jobs are bounded, build args are explicit, and ASan is opt-in with platform runtime requirements.

**Learning angle:** test harness fidelity includes execution environment, not only exit status.

## E. Ranked research candidates

1. **Manually unroll the existing 32-byte Mojo FNV probe** — yesterday proved clang fully unrolls the loop while Mojo 1.0 keeps a counted loop. Change only that mechanism, preserve checksum/workload/trials, verify hot-loop assembly, and measure x86_64 + arm64. This is the strongest unresolved canonical/codegen hypothesis.
2. **Float64 oracle hierarchy fixture** — one `std.math` primitive checked against system libm and, where available, a higher-precision oracle; focus on correctness classes before speed.
3. **Safetensors repeated-access decomposition** — mmap/open+validation versus repeated typed view access, with official Safetensors differential checks.
4. **Protobuf fixed-schema encode/decode** — external byte-level oracle, sizes swept, generation excluded from runtime timing.
5. **Python↔Mojo conversion boundary** — scalar to large-array round trips to find the amortization threshold.

The integrated research phase selects **exactly one** focused task; broad source collection does not imply multiple experiments.
