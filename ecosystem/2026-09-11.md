### O02. Grouped NVFP4 activation quantization removes sparse decode waste

**Freshness:** recent development, 2026-09-11.  
**Source:** https://github.com/modular/modular/commit/e468dc76d7f0bcee1c5aa23811d870f355b42ff3

The commit changes grouped NVFP4 activation quantization to skip empty rows, batch column tiles once occupancy is sufficient, and use a warp-parallel expert search. Its message reports a B200 decode case falling from roughly 31 µs to 7 µs and instruction count from 25.3M to 3.6M.

**Evidence boundary:** these are upstream measurements in the commit message, not reproduced here.

**Learning angle:** sparse workloads can make fixed-tile work dominate. A useful replication would sweep routed-row density while holding tensor shape and GPU/toolchain fixed.

### O03. Metal kernel-launch target selection moved to comptime

**Freshness:** recent development, 2026-09-11.  
**Source:** https://github.com/modular/modular/commit/84a11237607f61ecf48a92a444ff3f09505c514d

MAX previously selected Metal versus default launch paths with a runtime API-string condition, forcing both paths to be elaborated and code-generated at every `DeviceFunction` instantiation. The change makes target branching compile-time. The author reports a 20% end-to-end compile slowdown on Gemma4 from the old behavior.

**Why it matters:** compile-time specialization can be a *compiler throughput* optimization even when runtime kernel behavior is unchanged. This suggests a separate compile-time benchmark dimension for heavily instantiated GPU graphs.

### O04. Mojo 1.1 changelog cut for the release branch

**Freshness:** recent development, 2026-09-11.

## B. Repository discoveries — 12

### R01. `magmalake/iceberg-rs.mojo` — Apache Iceberg bridge and parity oracle

**Domain:** data lake / FFI / storage.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/magmalake/iceberg-rs.mojo

The project exposes Apache Iceberg to Mojo through a thin Rust `cdylib` over `iceberg-rust`, including scans, projection, snapshot selection, predicate pushdown and appends. Its most interesting design choice is methodological: the Rust bridge is explicitly retained as a **parity oracle** while native Mojo pieces are built.

**Evidence level:** repository documentation inspected; no local build performed.

**Research angle:** parity-oracle architecture is useful for migrating one subsystem at a time. A narrow experiment could replace exactly one codec/hash primitive with Mojo while checking byte-for-byte results through the existing Rust/PyIceberg path.

### R02. `visorcraft/MongrelDB-Mojo` — database client through Python stdlib interop

**Domain:** database / Python interop.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/visorcraft/MongrelDB-Mojo

This Mojo client uses Python's `urllib.request`, `json`, and `base64` through `Python.import_module`, while request/response logic remains in Mojo. It is a useful counterexample to assuming a Mojo application must be native end-to-end.

**Evidence level:** repository documentation inspected.

**Research angle:** measure the cost decomposition of one request path: Mojo-side shaping, Mojo→Python call boundary, Python HTTP/JSON work, and server time. Do not label total request latency a Mojo runtime benchmark.

### R03. `SergiuDeveloper/mojo-tensor` — explicit GPU autograd/training framework

**Domain:** GPU ML / autograd.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/SergiuDeveloper/mojo-tensor

The project implements tensors, a computational graph, SGD, dense layers, forward/backward GPU kernels and an MNIST training example. Unlike inference-only examples, it exposes the costs and correctness obligations of gradient propagation and parameter updates.

**Evidence level:** README/example architecture inspected; no training run reproduced.

**Research angle:** isolate a dense-layer forward/backward pair, validate against a high-precision reference, and separately measure kernel execution versus graph/setup overhead.

### R04. `ORNL/mojito` — performance-portable `parallel_for` / `parallel_reduce`

**Domain:** HPC / CPU-GPU portability.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/ORNL/mojito

ORNL's `mojito` presents higher-level CPU/GPU arrays and launch APIs that switch between CPU and vendor GPU backends. Its tests cover host/device allocation, copies and parallel kernels.

**Evidence level:** repository documentation/test output inspected; numbers not reproduced.

**Research angle:** one identical `parallel_reduce` workload could quantify abstraction/setup cost across CPU and GPU while preserving the same mathematical reduction and validation tolerance.

### R05. `labelrefinery/CenterPillars.mojo` — LiDAR-style perception pipeline

**Domain:** computer vision / geometry / ML inference.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/labelrefinery/CenterPillars.mojo

The repository contains a compact PointPillars/CenterPoint-like pipeline: point features, scatter-max pillar grid, backbone/neck/head, decoding and circle NMS. It documents per-stage parity reporting and hand-computed unit tests; `conv2d` is identified as the main hot loop.

**Evidence level:** repository documentation inspected.

**Research angle:** a deterministic `conv2d` or scatter-max micro-workload would add dense and irregular geometry operations without benchmarking an entire model.

### R06. `lee101/mojo-numpy` — bulk C-ABI kernels behind a NumPy-shaped Python layer

**Domain:** numerical computing / Python FFI.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/lee101/mojo-numpy

The project keeps Python-owned arrays and crosses into a Mojo shared library once per bulk operation, reconstructing raw pointers in Mojo. It documents SIMD reductions, parallel sorting, matrix microkernels and LU solve.

**Evidence level:** project methodology documentation inspected; published benchmark outcomes are author-reported.

**Research angle:** the boundary design is more interesting than headline speedups: compare one bulk operation at increasing sizes to locate the size where a single FFI call becomes amortized.

### R07. `gabrieldemarmiesse/mojo-zipfile` — native ZIP reader/writer

**Domain:** compression / file formats.  
**Freshness:** newly discovered existing project.  
**Repository:** https://github.com/gabrieldemarmiesse/mojo-zipfile

`mojo-zipfile` targets Python-like ZIP APIs with streaming reads/writes, ZIP64, DEFLATE, extraction and CRC32 verification.

**Evidence level:** repository documentation inspected.

**Research angle:** CRC32 is a compact independent workload with an unambiguous byte-level oracle. Compression throughput should be separated from checksum and filesystem I/O.

## D. Deep-dive picks

1. **`iceberg-rs.mojo` parity-oracle strategy** — a concrete migration architecture where a mature implementation remains available as a correctness reference while Mojo components replace it incrementally.
2. **Sep-11 MAX comptime target branch** — a strong example of a source-level specialization changing compiler throughput rather than runtime behavior.
3. **`CenterPillars.mojo` per-stage parity** — a useful pattern for validating multi-stage numerical pipelines instead of checking only the final output.
4. **`mojo-zipfile` CRC32** — a small byte-oriented workload that could broaden the benchmark suite without mixing parsing, allocation and hashing in one task.

## E. Ranked research candidates

1. **Fixed-width FNV-1a differential for Category C/D follow-up** — eliminate parsing/probing and compare only identical byte hashing across Mojo and C; this directly addresses the canonical open hash/parser/probe gap.
2. **CRC32 micro-workload inspired by `mojo-zipfile`** — verify against fixed vectors and compare scalar/SIMD implementations without filesystem I/O.
3. **Compile-time specialization cost** — construct a small repeated-instantiation test showing runtime target branching versus `comptime` branching and measure compile time/code size, inspired by the Sep-11 MAX fix.
4. **Iceberg parity-oracle methodology** — model one small replaceable codec/hash boundary with independent reference output.
5. **Image-pipeline fusion decomposition** — use MAX-CV as design inspiration, separating graph compile, transfer and steady-state kernel time.
