The public Modular tree now pins Mojo `1.2.0.dev2026092205` and MAX `26.7.0.dev2026092205`.

**Why it matters technically:** compiler-drift experiments need an exact package revision plus source SHA. A nightly pin is provenance, not a performance result; stable canonical results should remain separate from advisory nightly probes.

### O02. `TileTensor` dynamic slicing moves to Python-like subscript syntax

**Freshness:** recent development, merged 2026-09-22.  
**Canonical source:** https://github.com/modular/modular  
**Immutable source:** https://github.com/modular/modular/commit/7c14699ed8ef0091e8dbd9e95a80f3553587b08b

The GPU/layout layer now supports view-producing subscripts such as `t[batch, 0:n, :]`; compile-time `Idx[n]` components can fold into the view offset, while runtime slice bounds produce runtime extents. The previous `All` marker and two runtime slicing methods are removed.

**Why it matters technically:** this is both an API simplification and a code-generation boundary: compile-time indices and runtime slices intentionally share one syntax but should not necessarily have the same offset/extents cost.

**Evidence/maturity:** upstream implementation and changelog were inspected; no `mojo-analyze` runtime or assembly comparison was performed today.

**Research angle:** compare static `slice[]()` against equivalent runtime subscript slicing on a small strided tile operation, validating identical output and inspecting address arithmetic.

### O03. MAX adds media-resolution and preprocessing observability

**Freshness:** recent development, merged 2026-09-22.  
**Canonical source:** https://github.com/modular/modular  
**Immutable source:** https://github.com/modular/modular/commit/b87119a460323c3e306e9db2a8e6efd33c44f764

MAX serving adds `maxserve.media.*` metrics covering request item counts, inline/fetched media resolution time, per-item bytes, dimensions/format, decode cost, rejection causes, and preprocessing-cache pressure.

**Why it matters technically:** remote media fetch and decode can otherwise be folded into user-visible TTFT without attribution. The change makes I/O/decode/cache boundaries observable separately from model execution.

**Evidence/maturity:** upstream instrumentation change; it does not itself establish a throughput improvement.

**Research angle:** for multimodal benchmarks, record fetch/decode/preprocess/cache timings as separate phases rather than attributing end-to-end latency changes to kernels.

### O04. DP context-encoding planner fixes multiple admission/scheduling bugs

**Freshness:** recent development, merged 2026-09-22.  
**Canonical source:** https://github.com/modular/modular  
**Immutable source:** https://github.com/modular/modular/commit/afd44557678b7d7cd9c7656cafec020cd07b7c47

The distributed-serving scheduler fixes four data-parallel context-encoding balancing/admission cases that could mis-price or misplace work.

**Why it matters technically:** a serving benchmark can look like a kernel/runtime regression when the actual change is queue admission or placement. Scheduler correctness belongs in benchmark provenance whenever concurrency or multi-device placement is involved.

**Evidence/maturity:** correctness/scheduling change from upstream; no independent serving reproduction was attempted.

**Research angle:** if `mojo-analyze` later grows serving-style workloads, preserve scheduler/admission state in the evidence record rather than reporting only aggregate request latency.

### R01. `ttrenty/QLabs` — quantum circuit simulation in Mojo

**Owner/domain:** ttrenty — numerical/scientific / quantum simulation.  
**Freshness:** new discovery; existing project.  
**Canonical source:** https://github.com/ttrenty/QLabs

QLabs implements state-vector quantum circuits and gates in Mojo and includes package/test/benchmark tasks. The project is educational but technically useful because gate application is a compact, correctness-checkable numerical kernel with increasing state-vector size.

**Maturity/evidence:** README and benchmark layout inspected. The repository advertises large GPU speedups for larger qubit counts; those are **author-reported and not reproduced here**.

**Learning angle:** choose one gate sequence, validate final amplitudes against a Python/reference simulator, then sweep qubit count while separating host setup, transfer, and kernel time.

### R02. `leandrolcampos/specials` — accuracy-first special functions

**Owner/domain:** leandrolcampos — numerical math / special functions.  
**Freshness:** new discovery; older technical project.  
**Canonical source:** https://github.com/leandrolcampos/specials

`specials` implements functions such as `expm1`, `log1p`, `exp`, `log`, and related numerically sensitive routines with explicit emphasis on **accuracy before FLOP rate**. Its benchmark notebooks compare both accuracy and runtime against other implementations.

**Learning angle:** a modernized `expm1`/`log1p` oracle experiment should sweep difficult ULP regions first, then measure only implementations that satisfy the same accuracy contract.

### R03. `ihnorton/mojo-ffi` — low-level C/Mojo linking experiments

**Owner/domain:** ihnorton — FFI / linker/toolchain.  
**Freshness:** new discovery; technical backlog.  
**Canonical source:** https://github.com/ihnorton/mojo-ffi

The repository demonstrates three directions: calling C from Mojo, statically linking a Mojo executable with a C library, and producing a Mojo shared library callable from C. This is valuable as a record of ABI/linker boundaries rather than an application framework.

**Maturity/evidence:** only a handful of historical commits; scripts explicitly note missing macOS updates and may predate current supported tooling. Treat it as a compatibility probe, not current best practice.

**Learning angle:** compile the smallest C↔Mojo integer/byte-buffer round trip under Mojo 1.1/1.2, then measure boundary cost only after confirming ABI correctness.
