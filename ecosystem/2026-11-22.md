## Repository discoveries (16 identities; not necessarily new projects)

**Runtime, compiler & game/graphics**

- **R01 [Hundo1018/ludens-wasm-rt](https://github.com/Hundo1018/ludens-wasm-rt)** — *recent development, 2026-11-20*, owner Hundo1018, compiler/WASM. README describes retargeting Mojo-emitted x86-host LLVM IR to **wasm64**, linking a minimal runtime and host imports, then producing a module with LLVM tools. It explicitly says **Mojo 1.2 does not natively supply this target**, and documents that wasm32 is not supported; pinned LLVM 23.1.4, Node ≥24. New angle: compare module code sections with/without line-table DWARF and audit ABI imports. **Evidence:** README, project layout and dated commit; cross-compilation not independently performed.
- **R02 [Hundo1018/ludens-engine](https://github.com/Hundo1018/ludens-engine)** — *recent development, Nov 22*, owner Hundo1018, game runtime/UI/physics. Shared core targets a browser wasm64 module through host shells; native editor is a separate process, with `wgpu-mojo` and `miniaudio-mojo` boundaries. This is more than a geometry demo: frame pacing and physics profile hooks now expose an isolation point. **Evidence:** README and two immutable commits; current game features must not be confused with planned mobile/desktop shells. Suggested replication: fixed-step simulation checksum vs native/wasm64 tick costs.
- **R03 [create-framework/create](https://github.com/create-framework/create)** — *recent development, Nov 22*, owner create-framework, graphics/creative coding. Processing-inspired draw/animate, events, data, sound; CPU renderer with optional OpenGL backend. The dated `ui.changed()` interface change is technically relevant to input state reproducibility. **Evidence:** README, project/test directory, commit; no runtime compatibility test. Test identical scripted input traces and pixel hashes before comparing renderer time.
- **R04 [christianbator/mosaic](https://github.com/christianbator/mosaic)** — *new discovery*, owner christianbator, heterogeneous image processing. README describes image type/color-space, filters/transforms, CPU/GPU processing; project has separate `libmosaic-codec` and `libmosaic-fft` directories (dependency boundary matters). Latest inspected [Nov-09 commit](https://github.com/christianbator/mosaic/commit/3d935123c755b500d6b1d23b3563099abd1532fb) is documentation styling, **not** a material new kernel; don't overstate recency. **Evidence:** README and layout. Candidate: convolution against Pillow/OpenCV with pixel-error and transfer-cost accounting.
- **R05 [fnands/mimage](https://github.com/fnands/mimage)** — *older new discovery*, owner fnands, image codecs. README only claims simple **8-bit PNG reading**; explicitly states not fully pure Mojo and lists JPEG, complex PNG and output encoding as future work. **Evidence:** README; compatibility era/date unknown. Corpus idea: PNG chunk CRC, indexed/alpha/16-bit failure tests against Pillow, not throughput claims.
- **R06 [RyanLeber/fire-physics-engine](https://github.com/RyanLeber/fire-physics-engine)** — *older new discovery*, owner RyanLeber, physics/FFI. Box2D-lite-inspired 2D rectangle/pendulum demonstration with raylib C shim, WSL nightly-only validation disclosed by author; broad-phase replacement is roadmap. **Evidence:** README; modern Mojo compatibility unknown. Learning: isolate collision integration from raylib frame rendering and measure energy drift.
- **R07 [kivicode/mojo-raylib](https://github.com/kivicode/mojo-raylib)** — *new discovery*, owner kivicode, generated bindings and graphics. README reports generated raylib v6.x API coverage through a native shim, built using pixi; explicitly says not all APIs manually tested. **Evidence:** README, shim/vendor/examples layout. FFI smoke-test struct layouts, callbacks and platform-dependent behavior; generated coverage ≠ runtime validation.
- **R08 [davidmashburn/moxi](https://github.com/davidmashburn/moxi)** — *recent development, Nov 20*, owner davidmashburn, reactive UI/visualization. Xilem-inspired retained reconciliation, ordered paint-command stream for native/Metal/software renderers, headless golden images and platform-specific support. **Evidence:** README/layout and commit. Cross-backend deterministic pixels and UI transaction semantics are stronger tests than screenshot claims; macOS Apple Silicon feature depth differs from provisional Linux.

## Deep-dive picks (synthesis only, not counted again)

1. **WASM portability without pretending native compiler support** (R01/R02): compare wasm64 vs native identical application simulation checksums; separate runtime-import/host-frame overhead, track compiler and LLVM pins.
2. **Numerical semantics as first-class performance prerequisites** (R12/R13/R14): NaN reductions, singular solves, tail probabilities and BLAS strides before speedup claims.
3. **Geometry and image processing separation** (R03–R08): image/physics correctness oracles and CPU/GPU/FFI transfer accounting; changes in widget event semantics are not codegen improvements.
4. **Data-system baseline discipline** (R09–R11/R16/T05): search recall, HDF5 roundtrip and SQL results checked with reference implementations; C native dependencies/FFI must be named.
5. **Compiler-era compatibility** (R01/T01/T06): pinned nightly, stable 1.2, x86/WASM retargeting and dated old proposals should not be mixed as equivalent implementations.

## Research candidates (ranked; one to select in Phase 2)

1. **Existing canonical arm64 checked-Span scanner hypothesis** — region-scoped CPU clocks, correctness checksum, paired trials and ARM64 assembly under pinned Mojo (requires native arm64 runner; don't fake results).
2. **ludens-wasm-rt wasm64/native correctness and debug-info invariant** — compile same `hello_kernel`, check identical code and type sections with/without `--debug line-tables`; compare native/wasm64 deterministic output, only if pinned toolchains available.
3. **Linamo NaN/singular-matrix oracle** — test NaN propagation and singular inverse/solve against NumPy with exact inputs, version/toolchain pinned.
4. **HDF5 FFI round-trip oracle** — randomized compressed/chunked multidimensional arrays against h5py, boundary-focused.
5. **MojoVec recall@k × latency × memory frontier** — HNSW/SQ8 vs matched hnswlib, fixed build/search parameters and deterministic data.
