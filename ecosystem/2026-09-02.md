# Mojo Ecosystem Radar — 2026-09-02

First ecosystem brief for `mojo-analyze`. This report focuses on technically meaningful developments that can generate follow-up experiments rather than general popularity signals.

## Official Mojo / Modular updates

### Mojo 1.0 is now stable

Modular released Mojo 1.0 on 2026-08-11. The 1.x line introduces source-stability expectations: changes should mostly be additive, with breaking changes managed more conservatively. The 1.0 release also finalized a round of language simplification around `var`, closures, `Pointer`, diagnostics, lambda syntax, memory-safety diagnostics, `where` clauses, and a more reliable LSP.

Why it matters for this repo: `mojo-analyze` can now start treating Mojo 1.x as a stable longitudinal benchmark target instead of a rapidly moving prerelease language. A version-history benchmark suite is now more meaningful.

Sources:
- https://www.modular.com/blog/modular-26-5-mojo-1-0-is-here
- https://mojolang.static.modular.com/releases/v1.0.0/

### The Mojo compiler and toolchain are now open source

On 2026-08-18, Modular open-sourced the full Mojo language, compiler, and tooling under Apache 2.0 with LLVM exceptions. The main `modular/modular` repository now exposes compiler internals under `KGEN`, alongside the standard library and MAX kernels.

Why it matters: performance investigations no longer need to stop at emitted assembly. `mojo-analyze` can increasingly trace surprising codegen through compiler passes, lowering decisions, and open compiler issues.

Sources:
- https://www.modular.com/blog/mojo-open-source
- https://www.modular.com/blog/modcon-announcements
- https://github.com/modular/modular

### Hardware scope is broadening

At ModCon, Modular announced platform work spanning AWS Trainium, Google TPUs, Qualcomm accelerators, CPUs and GPUs, plus forthcoming native Windows support for Mojo. MAX also continues to expose portable accelerator primitives in Mojo.

Why it matters: cross-platform benchmarking can eventually expand beyond macOS arm64 / Linux x86_64 / Linux arm64 into a more explicit backend-comparison project.

Source:
- https://www.modular.com/blog/modcon-announcements

## Notable Mojo repositories and experiments

### `ehsanmok/json` — high-performance JSON with CPU SIMD and GPU backends

Repository: https://github.com/ehsanmok/json

This is especially relevant to `mojo-analyze` category E. It uses a pure-Mojo two-pass parser with a 64-byte branchless SIMD structural scan, a tape-backed document representation, GPU parsing across NVIDIA / AMD / Apple Metal, and an optional simdjson FFI comparison. The project explicitly reports that stripping stdlib safety assertions changes benchmark performance by roughly 20–37% on its workloads.

Why interesting: `mojo-analyze` just established that category E's byte-at-a-time scanning loop is the remaining bottleneck after inlining. This repo demonstrates the next algorithmic step that the current analysis predicts: structural pre-indexing plus SIMD.

Potential replication: build a minimal structural-index stage inside category E and compare byte-at-a-time scan vs branchless SIMD scan while preserving the existing checksum contract.

### `sbrunk/duckdb.mojo` — Mojo bindings plus transparent GPU query offload

Repository: https://github.com/sbrunk/duckdb.mojo

The project provides Mojo bindings for DuckDB and a GPU operator extension that can transparently offload supported aggregation/filter/join plans and vector-search top-k operations to Mojo GPU kernels, with fallback to normal DuckDB. It supports NVIDIA and Apple GPUs and ships comparative benchmark tooling.

Why interesting: this moves Mojo benchmarking from isolated kernels toward realistic query-engine integration and mixed CPU/GPU execution.

Potential replication: add a compact analytical query benchmark to `mojo-analyze` that compares CPU SIMD, GPU with per-call upload, and GPU with preloaded data. This would test transfer-amortization behavior directly.

### `kszucs/marrow` — Arrow implementation in Mojo

Repository: https://github.com/kszucs/marrow

`marrow` implements Arrow-oriented data processing in Mojo with CPU SIMD and GPU acceleration. Its published examples show an important crossover pattern: low-arithmetic-intensity elementwise work remains faster on CPU SIMD, while preloaded GPU cosine similarity becomes substantially faster as dataset size grows.

Why interesting: this is a clean real-world demonstration that GPU wins depend strongly on data residency and arithmetic intensity, matching `mojo-analyze`'s existing finding that several GPU ports lose to CPU.

Potential replication: formalize GPU crossover curves in this repo rather than recording one workload size per category.

### `ulmentflam/llm.mojo` — GPT-2 training in pure Mojo

Repository: https://github.com/ulmentflam/llm.mojo

This project implements GPT-2 training in pure Mojo with handwritten CUDA and Metal GPU kernels, including comparisons against `llm.c` and PyTorch. It reports bf16 parity with `llm.c` on NVIDIA in one published campaign and a Metal implementation compared with PyTorch MPS on Apple Silicon.

Why interesting: it is one of the stronger examples of Mojo being used as a full application-level GPU systems language rather than a microbenchmark language.

Potential replication: extract one self-contained primitive (layer norm, softmax, matmul wrapper, optimizer update) and compare Mojo vs a mature baseline under `mojo-analyze`'s stricter reproducibility/checksum methodology.

### `ORNL/mojito` — performance-portable `parallel_for` / `parallel_reduce`

Repository: https://github.com/ORNL/mojito

Oak Ridge National Laboratory's `mojito` explores a higher-level API that switches between CPU and supported GPU backends while keeping a shared array/kernel programming model.

Why interesting: it tests whether Mojo can support a Kokkos-style performance-portability abstraction without losing the low-level advantages that motivate Mojo in the first place.

Potential replication: compare a hand-written Mojo kernel against a higher-level portability abstraction for the same reduction workload and quantify abstraction overhead.

### `andomeder/mojo-intel-gpu` — Intel GPU compute through Level Zero FFI

Repository: https://github.com/andomeder/mojo-intel-gpu

This project drives Intel GPUs through Level Zero FFI from Mojo, with vector addition, matrix multiplication, reductions, memory-transfer tests, and dispatch-latency benchmarking.

Why interesting: it explores accelerator access outside the most common built-in Mojo GPU paths and is a useful FFI/system-boundary case study.

Potential replication: introduce a small FFI-overhead benchmark category measuring call/dispatch overhead independently from kernel execution time.

### `nktkt/mojo-flash-attention` — readable FlashAttention-style kernels

Repository: https://github.com/nktkt/mojo-flash-attention

The project implements exact streaming attention on CPU and GPU, validates against CPU references, and includes an Apple GPU block kernel that reportedly improves substantially over its scalar GPU version. It deliberately stops short of a tensor-core implementation, leaving a clear optimization path.

Why interesting: it has the same philosophy as `mojo-analyze`: correctness first, then controlled optimization with explicit baselines.

Potential replication: use attention as a future category for testing scalar → SIMD/block → MMA/tensor-core optimization stages.

### `mikeleppane/mojo-rust-python-perf` — cross-language benchmark suite

Repository: https://github.com/mikeleppane/mojo-rust-python-perf

This project compares Mojo, Rust, Python, PyPy and NumPy on classic workloads such as n-body and pidigits. Its n-body results distinguish naive Mojo from an explicit SIMD version, making it useful as an external comparison point for `mojo-analyze`'s conclusion that Mojo's strongest wins appear when the implementation exposes SIMD-friendly structure.

Why interesting: useful benchmark-overlap candidate and methodology comparison rather than a source of numbers to copy directly.

Potential replication: independently reproduce one workload using `mojo-analyze`'s checksum-gated harness and compare methodology-sensitive conclusions.

## Compiler / codegen issue worth tracking

### Apple GPU GEMM gap vs hand-written Metal

Issue: https://github.com/modular/modular/issues/6870

A recent Modular issue reports a structurally matched Mojo Apple-GPU GEMM kernel around 1.69x slower than hand-written Metal, with tile shape, dtype, ownership, load width and other structural choices intentionally held equal.

Why interesting: now that the compiler is open source, this is exactly the kind of gap that can be investigated below the source level rather than attributed vaguely to "compiler maturity".

Potential replication: create a reduced Apple-GPU codegen case and compare generated Metal/LLVM lowering decisions, register pressure, memory operations, and instruction scheduling.

## Ecosystem direction

The strongest signal today is not a brand-new release on 2026-09-02, but the post-1.0 ecosystem shift. Mojo now has a stable 1.x baseline and an open compiler at the same time that community projects are moving from demos into JSON parsers, Arrow-style data systems, DuckDB extensions, LLM training, attention kernels, portability layers, and cross-vendor GPU access.

For `mojo-analyze`, the most valuable next step is therefore to evolve from "which language is faster on five tasks?" toward "which implementation and compiler mechanisms explain the gap?".

## Research candidates

1. **Category E structural scan prototype** — borrow only the algorithmic idea from `ehsanmok/json`: structural pre-indexing + branch-reduced/SIMD scanning, while retaining this repo's own implementation and checksum contract.
2. **GPU crossover benchmark mode** — sweep input sizes and distinguish upload-per-call from preloaded-device-data execution, inspired by `marrow` and `duckdb.mojo`.
3. **Mojo 1.x longitudinal benchmark history** — preserve benchmark snapshots by compiler version to detect performance regressions/improvements across 1.x.
4. **Open-compiler codegen investigations** — for any persistent Mojo-vs-C/Rust gap, link source benchmark → emitted assembly → relevant KGEN lowering/pass where feasible.
5. **Abstraction-cost experiment** — compare hand-written kernel vs a `parallel_for`-style abstraction using the same workload and generated-code inspection.
