## Important current developments

### O01. Sep-10 nightly: Mojo 1.1.0.dev2026091005 / MAX 26.6.0.dev2026091005

**Freshness:** recent development, 2026-09-10.  
**Source:** https://github.com/modular/modular/commit/48d33430b478f47fea76c0bb01b5246fa26989e1

The public lockfiles advanced to **Mojo `1.1.0.dev2026091005` and MAX `26.6.0.dev2026091005`**. This is the exact package revision to use for any Sep-10 stable/nightly comparison; a branch timestamp alone is insufficient provenance.

**Why it matters:** `mojo-analyze` should continue recording exact package revisions/hashes when comparing compiler generations rather than saying only “latest nightly.”

### O02. `nextafter` now works in the comptime interpreter

**Freshness:** recent stdlib change, 2026-09-10.  
**Source:** https://github.com/modular/modular/commit/9304e8bc2750688f6f47375fa2a3d4421a5595de

At runtime `nextafter` can call libc, but the comptime interpreter cannot execute that external C call. The new comptime path steps IEEE-754 bit patterns directly while leaving the runtime libc path intact. The change adds edge-case tests and reports a broad random float32 cross-check against libc with bit-identical results.

**Why it matters:** this is a strong example of a language/runtime split where a compile-time implementation can be independently checked against the runtime oracle. A future codegen probe could also verify that the comptime branch folds away from runtime code as intended.

### O03. `Counter` accepts arbitrary `Iterable` input

**Freshness:** recent stdlib API change, 2026-09-10.  
**Source:** https://github.com/modular/modular/commit/c7d030f1d19a4881224232a9fc9e7f55a373e778

`Counter` gains an initializer from any `Iterable`, replacing the narrower `List` constructor while preserving type inference. Tests cover list literals/variables, empty iterables, Unicode strings, and byte iteration.

**Why it matters:** this is directly relevant to data-processing ergonomics, but it is not evidence that `Counter` is a faster replacement for the hand-rolled hash table in Category C. API convenience and benchmark technique remain separate questions.

### O04. AMD MXFP6 matmul tuning advances while MAX adds DFlash2

**Freshness:** recent MAX/kernel work, 2026-09-10.  
**Sources:** https://github.com/modular/modular/commit/3c821890811316b8bc91abda757a03b1476f78ad and https://github.com/modular/modular/commit/aaf760f8012df0dba6df04eb8329b9dc82bc7a9d

The kernel tree tunes MXFP6 block-scaled matmul bands on AMD CDNA4, while MAX adds a DFlash2 block-diffusion speculative drafter architecture for Qwen3.8-27B. These are separate mechanisms grouped here as the strongest same-day accelerator signal rather than counted as multiple filler entries.

**Why it matters:** the ecosystem is moving beyond generic “GPU support” into architecture-specific quantized kernel tuning and alternative speculative-decoding shapes. Any replication needs matching hardware/model/runtime conditions rather than importing an internal headline number.

## Repository discoveries

### R01. ExtraMojo — practical stdlib extensions with SIMD byte utilities

**Repository:** https://github.com/ExtraMojo/ExtraMojo  
**Owner/domain:** ExtraMojo — stdlib utilities / data structures.  
**Freshness lane:** new discovery; README inspected; current example pins Mojo 1.0.0.

ExtraMojo collects functionality missing from the stdlib: buffered file I/O, CLI parsing, SIMD `memchr`/case conversion/splitting for byte strings, BBHash, BitVec, saturating arithmetic and reservoir sampling.

**Why interesting:** several components are small enough for fair isolated experiments without importing an entire framework.  
**Experiment angle:** compare one SIMD byte primitive against a scalar Mojo loop with identical bytes/output and inspect emitted assembly.

### R02. Mojmelo — classical machine learning implemented in pure Mojo

**Repository:** https://github.com/yetalit/Mojmelo  
**Owner/domain:** yetalit — classical ML.  
**Freshness lane:** new discovery; README inspected; requires Mojo compiler 1.0.0+.

Mojmelo implements linear/logistic regression, clustering, SVM, naive Bayes, trees/forests/GBDT, PCA and preprocessing from scratch in Mojo, with optional Python packages used for testing/usability rather than as the implementation engine.

**Why interesting:** it broadens the ecosystem beyond neural-network/GPU examples into branchy, data-dependent classical algorithms.  
**Experiment angle:** one small K-means assignment or tree-inference kernel with a reference output; do not generalize package-wide author benchmark claims.

### R03. mojo-regex — hybrid DFA/NFA/PikeVM/LazyDFA regex engine

**Repository:** https://github.com/msaelices/mojo-regex  
**Owner/domain:** msaelices — parsing / automata / compiler techniques.  
**Freshness lane:** new discovery; README and benchmark/design surface inspected.

The engine selects among DFA, NFA/PikeVM and LazyDFA strategies and has an experimental compile-time pattern mode where accepted patterns build an automaton during compilation and embed it in the binary. Unsupported compile-time cases fall back to the runtime engine.

**Why interesting:** it exposes a clean compile-time-versus-runtime work-placement question. The README's Python/Rust comparison percentages are author measurements, not reproduced here.  
**Experiment angle:** fixed pattern/text corpus comparing runtime compilation, cached matching and comptime-embedded matching, with identical match spans and build-time/code-size accounting.

### R04. mojoBLAS — pure-Mojo BLAS levels 1–3

**Repository:** https://github.com/shivasankarka/mojoBLAS  
**Owner/domain:** shivasankarka — numerical linear algebra.  
**Freshness lane:** new discovery; README inspected; Mojo `>=1.0.0,<2`.

mojoBLAS implements BLAS Level 1, 2 and 3 routines in Mojo and ships its own comparison suite against reference/system BLAS.

**Why interesting:** it provides established numerical kernels with well-known correctness contracts, while still requiring careful disclosure of dtype, layout, threading and the system BLAS comparator.  
**Experiment angle:** isolate one small GEMV or AXPY shape and validate numerical tolerance before timing; avoid package-wide “Mojo vs BLAS” claims.

### R05. mojo-intel-gpu — Level Zero FFI for Intel GPU compute

**Repository:** https://github.com/andomeder/mojo-intel-gpu  
**Original showcase:** https://forum.modular.com/t/mojo-intel-gpu-v0-1-0-level-zero-ffi-for-intel-gpu-compute-mojo-v1-0-0b1/3253  
**Owner/domain:** andomeder — GPU driver FFI / portability.  
**Freshness lane:** technical discovery/backlog; original June 18, 2026 showcase.

The project exposes Intel Level Zero device/buffer/kernel abstractions from Mojo; kernels are compiled from OpenCL C to SPIR-V and loaded through Level Zero. The author lists current limitations around synchronous command handling, low-level subgroup/SLM exposure and single-device selection.

**Why interesting:** it is a non-CUDA/non-MAX route to GPU control, but the actual kernel code is not Mojo GPU codegen.  
**Experiment angle:** measure host-side launch/copy overhead separately from SPIR-V kernel execution and state the driver/compiler stack explicitly.

### R06. ML Odyssey — large Mojo-native training/autograd framework

**Repository:** https://github.com/HomericIntelligence/Odyssey  
**Owner/domain:** HomericIntelligence — ML training / autograd.  
**Freshness lane:** new discovery; README inspected.

The project describes a reusable SIMD-oriented tensor/autograd/training stack plus several reproduced neural-network architectures, with a large Mojo codebase and test suite. Its README explicitly distinguishes the ML framework from similarly named agent infrastructure in the same organization.

**Why interesting:** it is evidence of Mojo being used for a large application codebase, not just isolated kernels.  
**Experiment angle:** extract one documented tensor primitive with a small reference rather than trying to benchmark the entire training stack.

### R07. MMMAudio — real-time sound synthesis in Mojo + Python control

**Repository:** https://github.com/mmmaudio/mmmaudio  
**Owner/domain:** mmmaudio — audio / DSP.  
**Freshness lane:** new discovery; README inspected; associated with an ICMC 2026 paper.

MMMAudio uses Mojo for real-time DSP and Python as the scripting/control layer, emphasizing parallel SIMD CPU processing, single-sample feedback and oversampling. It supports Mac/Linux including Raspberry Pi on Ubuntu.

**Why interesting:** real-time audio adds latency, jitter and signal-correctness constraints missing from throughput-only benchmark suites.  
**Experiment angle:** one oscillator/filter/FFT block with fixed buffer size and numerical tolerance, reporting both throughput and per-buffer latency.

### R08. MojoSplat — 3D Gaussian Splatting kernels called from PyTorch

**Repository:** https://github.com/bertaveira/mojosplat  
**Owner/domain:** bertaveira — graphics / GPU / Python interop.  
**Freshness lane:** new discovery; README and benchmark description inspected; explicitly experimental.

The project implements projection, binning and rasterization kernels in Mojo and exposes them to PyTorch. Its published RTX 5090 comparison reports the Mojo rasterizer close to gsplat while binning remains slower; those numbers are author measurements and the first render also pays a documented JIT cost.

**Why interesting:** the per-stage breakdown prevents a whole-pipeline number from hiding the true gap.  
**Experiment angle:** if matching hardware exists, reproduce one deterministic projection or binning stage and separately measure Python↔Mojo/JIT overhead.

### R09. gsplat_mojo — end-to-end MAX custom-op Gaussian splatting

**Repository:** https://github.com/sandeepnmenon/gsplat_mojo  
**Owner/domain:** sandeepnmenon — graphics / GPU / MAX custom ops.  
**Freshness lane:** new discovery; README inspected; current tree targets Mojo `1.1.0.dev` and Linux x86_64.

The forward path covers PLY loading, spherical harmonics, projection, two-level scan, radix depth sort and rasterization, and can run natively or as a MAX custom op. The project documents reference checks for synthetic scenes and a real 329k-Gaussian asset, but has no backward pass and a finite scan capacity.

**Why interesting:** it provides a contrasting architecture to MojoSplat: a packaged Mojo/MAX custom-op path rather than a PyTorch-first wrapper.  
**Experiment angle:** study one scan/sort phase with a deterministic CPU reference before treating full-render image agreement as a performance proof.

### R10. mojo-bindgen — C headers to Mojo FFI with conservative ABI fallbacks

**Repository:** https://github.com/MoSafi2/mojo_bindgen  
**Owner/domain:** MoSafi2 — FFI / binding generation.  
**Freshness lane:** new discovery; current README inspected; Mojo 1.0+ for generated bindings.

mojo-bindgen parses real C with libclang, maintains a structured IR, supports `external_call` and dynamic `OwnedDLHandle` modes, and emits typed layouts where faithful while falling back to opaque storage for hostile ABI cases. Real examples include SQLite, Cairo, libpng and zlib.

**Why interesting:** “fail conservatively” is the right correctness posture for generated ABI code.  
**Experiment angle:** generate bindings for a compact fixed C header and validate struct sizes/offsets, callbacks and runtime calls before measuring generation/build cost.

### R11. Mojo BenchSuite — suite-level benchmark orchestration

**Repository:** https://github.com/DataBooth/mojo-benchsuite  
**Owner/domain:** DataBooth — benchmarking / methodology.  
**Freshness lane:** new discovery; README inspected.

BenchSuite adds benchmark discovery, adaptive calibration, p50/p95/p99 reporting, environment-aware output, saved baselines, regression thresholds and JSON/CI integration around Mojo's benchmark primitives.

**Why interesting:** it addresses suite workflow rather than replacing the low-level timer.  
**Experiment angle:** compare its adaptive estimator against `mojo-analyze`'s fixed-trial method on one stable microbenchmark, focusing on estimator stability and overhead rather than who reports the smallest time.

### R12. MXFrame — cross-vendor GPU dataframe/query engine

**Repository:** https://github.com/abhisheksreesaila/mxframe  
**Original showcase:** https://forum.modular.com/t/mxframe-cross-vendor-gpu-dataframes-with-mojo-aot-kernels/3358  
**Owner/domain:** abhisheksreesaila — GPU dataframes / query processing.  
**Freshness lane:** technical discovery/backlog; original July 30, 2026 showcase.

MXFrame presents a Polars-style lazy API backed by precompiled Mojo AOT kernels targeting NVIDIA, AMD and Apple Silicon. The author reports large speedups on selected joins; these are **replication targets**, not evidence imported into `mojo-analyze`.

**Why interesting:** it offers real cardinality/skew-sensitive joins and group-by workloads, exactly the kind of data-processing direction missing from the current five categories.  
**Experiment angle:** a small controlled join with explicit key cardinality, skew, transfer cost and checksum/row-count validation.

## Deep-dive picks

1. **mojo-regex:** unusually clean separation between compile-time automaton construction and runtime matching, suitable for measuring where work moves rather than only total speed.
2. **mojo-bindgen:** conservative ABI modeling plus runtime smoke tests make it a useful correctness architecture for Mojo's still-evolving FFI ecosystem.
3. **MojoSplat / gsplat_mojo:** two distinct integration strategies around the same graphics workload expose Python/JIT/custom-op boundaries and per-stage GPU bottlenecks.
4. **MXFrame:** cardinality/skew-sensitive query workloads are a promising path beyond the repo's current parser/hash-heavy categories.
5. **ExtraMojo:** its small SIMD byte primitives can become low-cost, assembly-verifiable compiler experiments without changing a canonical benchmark prematurely.

## Research candidates

1. **Category D Mojo slot-storage differential** — strongest unresolved canonical hypothesis: replace only the five fixed-capacity `List` slot arrays with raw pointers, preserve FNV/probing/parser/checksum semantics, inspect emitted assembly where useful, and run 2 warmups + 7 trials on Linux x86_64/arm64. Category C's earlier negative result makes this a falsification-oriented experiment, not an assumed optimization.
2. **ExtraMojo SIMD byte primitive** — scalar vs SIMD `memchr`/case conversion with identical bytes and assembly inspection.
3. **mojo-regex comptime work-placement probe** — separate build cost, runtime pattern compilation and match time on one fixed corpus.
4. **MXFrame-style controlled join workload** — fixed cardinality/skew and explicit transfer/setup boundaries.
5. **Mojo BenchSuite estimator cross-check** — adaptive calibration versus fixed-trial reporting on a stable Mojo microbenchmark.
