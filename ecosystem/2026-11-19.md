## Recent developments and repository discoveries

### R01 — PyroMojo: Python-library semantics before performance
- **Repository/owner:** https://github.com/adarshsoloman/pyromojo — adarshsoloman. **Lane:** newly discovered repository with November 18, 2026 original showcase https://forum.modular.com/t/i-am-porting-python-libraries-to-mojo-pyromojo-4-native-mojo-v1-2-0-ports-of-foundational-python-libraries-verified-honestly-benchmarked/3679 . **Observed:** November 19. **Domains:** binary serialization, string algorithms, packed bits, audio codecs.
- **Technical substance:** Four separately versioned Mojo 1.2.0 ports: MessagePack (162 golden vectors), Levenshtein (434), Bitarray (266), Audioop (1,277, covering 26 CPython 3.12 operations). The planned resampy port is *not shipped*. README distinguishes a pure Python baseline from optimized native C/C++ upstream, and requires exact output/state parity before timing.
- **Evidence:** README inspected through connected GitHub, and original author showcase read. The author reports Bitarray's byte-serial 1-Mibit operations losing to 64-bit-word native C; MessagePack's binary encode slower despite small-map wins; Audioop slower than optimized C in aggregate. These are **author-reported** and not independently replicated. Test vectors and CI badges are evidence of a testing approach, not proof of independent reproducibility; individual implementation paths were not audited in this pass.
- **Research:** isolate bitarray word-parallel vs byte-serial operations under identical memory layout and checksum, or independently validate MessagePack boundary vectors before comparing encode throughput. Do not import author timings into canonical benchmark charts.
