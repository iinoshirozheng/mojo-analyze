## Systems / networking: `mojo-http` adds spawn workers and explicit accept sharing

Repository: https://github.com/codetalcott/mojo-http

### Fresh-process workers solve fork-hostile runtime integration

Commit `0d11fa53` adds `--spawn-workers`: the supervisor still forks, but each worker immediately `execv`s a fresh image and reconstructs listener/shared-state descriptors. This was motivated by real macOS integrations where forked children are unsafe: Core ML refused to run correctly after fork, and macOS proxy lookup through `urllib` also failed in the forked shape. The measured startup cost was small in the reported A/B (roughly 82 ms forked vs 92 ms spawned), while hello-world throughput was effectively unchanged.

Why interesting: this is a concrete example of choosing process semantics based on foreign-runtime invariants rather than generic "fork is cheaper" folklore. Mojo systems code that embeds Python, Objective-C/Core ML, GPU runtimes, or other stateful native libraries may need a fresh executable image even when file descriptors and shared state are intentionally preserved.

Source:
- https://github.com/codetalcott/mojo-http/commit/0d11fa531a954216aea11a6ec38a946f185212d0

### Shared listener was not enough: accept ownership had to be redistributed explicitly

Commit `85f3e49a` measures a second multiprocessing failure mode. With multiple workers waiting on one listener, bursts of keep-alive connections were heavily skewed toward one worker (32/0 on macOS and typically 23–31 of 32 on Linux). The project rejected two intuitive fixes after measurement: `SO_REUSEPORT` on macOS still concentrated connections, while an nginx-style accept token only moves the right to accept, not an already accepted persistent connection.

The implemented `AcceptShare` path passes the accepted socket to the least-loaded sibling via `SCM_RIGHTS`, tracking `active + pending` load per worker. The reported result was 16/16 distribution in the tested two-worker shapes; a Core ML workload with two spawned workers improved from 1779 to 3090 req/s at concurrency 8, compared with 2510 for uvicorn's two-worker reference.

Why interesting: for long-lived/keep-alive workloads, fair *accept wakeups* and fair *connection ownership* are different problems. A benchmark that only reports aggregate throughput can miss a severe worker-distribution pathology.

Potential `mojo-analyze` experiment: if a networking category is added, record per-worker accepted-connection counts and load distribution alongside requests/sec. Treat fairness as a correctness/performance dimension rather than only measuring total throughput.

Sources:
- https://github.com/codetalcott/mojo-http/commit/85f3e49a8f98c4122bf7ba00b3f648a4fa8b311f
- https://github.com/codetalcott/mojo-http/commit/e0e454ffc05454d5ea98028a8023d42eb6334d12

### Core ML embedding serving provides an interoperability case study

Commit `b6cce40f` records a MiniLM/Core ML serving comparison on Apple Silicon. In the reported one-process comparison, the Mojo server served the GIL-holding Core ML predict path at 1684 req/s vs 1444 for uvicorn, with lower p99 latency; increasing a thread pool did not help because the inference call retained the GIL. The work directly led to the fresh-process worker and accept-sharing changes above.

Why interesting: it is a useful reminder to decompose an "interop performance" result into at least three layers: runtime ownership (GIL/thread state), process creation semantics, and connection/work distribution. Improving only one can leave the application bottleneck unchanged.

Source:
- https://github.com/codetalcott/mojo-http/commit/b6cce40f54180cbc8fb6d8e28ad2e030c9e33003

## Benchmark methodology: `mojo.httpx` builds a serious non-CI performance suite

Repository: https://github.com/tamnd/mojo.httpx

Commit `0f81b217` adds ten benchmark cases covering sequential keep-alive, concurrent requests, 10 MiB upload/download, HTTP/2 streams, cold starts, and header/HPACK/URL microbenchmarks. Each case runs in its own process; the driver takes the best of several runs and can gate regressions against a machine-specific baseline.

The more important design choice is what it deliberately does **not** do: the 5% performance gate is kept out of shared CI because noisy runners would produce false regressions, and no baseline is committed until a sufficiently idle machine can produce one worth comparing against.

Why interesting for `mojo-analyze`: this complements yesterday's repeated-relative-ratio lesson. There are two distinct benchmark products:

1. controlled-machine regression gates, where a machine-specific absolute baseline can be meaningful;
2. shared-runner cross-platform evidence, where repeated relative ratios are safer than hard absolute thresholds.

Potential experiment/infrastructure change: keep GitHub-hosted runner jobs advisory, but add an optional local/controlled-host regression command that compares current results against a machine-keyed baseline and records raw samples.

Source:
- https://github.com/tamnd/mojo.httpx/commit/0f81b217480d4c43b1848861eb86646d9f8e377d

## Async / compiler-lowering watch: HTTPS works, but requires an explicit no-inline seam

`mojo.httpx` commit `2f424efd` adds asynchronous HTTP/1.1 TLS without a second TLS implementation: the existing non-blocking OpenSSL-backed stream is advanced one step at a time and the coroutine decides whether to wait for read or write readiness.

The compiler-specific detail is more interesting than the feature itself: `_connect_step` is marked `@no_inline` because inlining exception/string-building logic into the coroutine loop reportedly causes Mojo to crash during coroutine lowering with an invalid-value-index error. The no-inline boundary keeps the landing-pad-heavy helper out of the suspension transform.

Why interesting: `@no_inline` can be a compiler-stability boundary, not merely a performance hint. This is worth tracking in stable-vs-nightly differential tests because an eventual compiler fix should let the workaround disappear without changing semantics.

Potential `mojo-analyze` experiment: create a tiny compile-only coroutine regression probe with an inlined vs `@no_inline` exception-heavy helper. Track compile success and emitted code across stable/nightly; do not put it in the canonical runtime scoreboard.

Source:
- https://github.com/tamnd/mojo.httpx/commit/2f424efd9878ed41451a6a0ec79c8ac1be8d9a01

## Public API / documentation quality signals

`mojo.httpx` also added two useful tooling patterns today:

- commit `9e9adbf3` batches independent documentation examples into one compiler invocation, reducing a reported doc-example build from 97 s to 13 s while isolating examples that declare top-level names;
- commit `e820493b` derives a public API census from the same export surface used by generated docs, then requires every public name to appear in tests (with explicit narrow exceptions).

These are not performance benchmarks for `mojo-analyze`, but they are relevant to a growing Mojo codebase: compiler startup/package-build cost can dominate many tiny compile probes, and the canonical definition of a public surface should be reused by docs/tests rather than independently reconstructed.

## Newly surfaced research-style Mojo project

### `labelrefinery/OfflinePoly.mojo` — pure-Mojo geometry/combinatorics pipeline

Repository: https://github.com/labelrefinery/OfflinePoly.mojo

This is a from-paper pure-Mojo implementation of a learning-free offline 3D multi-object-tracking pipeline: rotated-box geometry, motion extrapolation, graph matching, least-squares refinement, CSV I/O and synthetic-scene tests. The initial implementation landed Aug 28 and CI was refreshed Sep 3 for current Pixi tooling.

Why interesting: unlike AI-kernel demos, the workload is mostly geometry, matching, branching and small dense math. It could provide a future application-level source for benchmark kernels that stress very different codegen than the current sieve/string/JSON categories.

Potential experiment: do **not** benchmark the full tracker first. Extract one deterministic primitive such as rotated-box IoU or assignment-cost construction, establish byte/numeric correctness tolerance, then compare Mojo/C/Rust implementations with the same algorithm.
