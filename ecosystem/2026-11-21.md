## Newly discovered / deeper repository profiles

### R01 — bajo: GPU BVH and path-tracing foundation (geometry, rendering, prospective physics)

- **Source/owner:** https://github.com/jgsimard/bajo — Jean-Gabriel Simard; **lane:** newly examined repository (creation date not asserted); observed November 21.
- **Direct evidence:** Connected GitHub README inspected on `main`. It documents OBJ/MTL and PBRT scene loading, CPU/GPU BVHs, GPU sorting, CPU/GPU path tracing, and a Mojo viewer with raylib 6.2. It explicitly calls particle/fluid/rigid-body simulation and batched environments **planned**, not shipped. The interactive viewer supports path tracing with PATH/NEE/MIS and CPU/GPU selection.
- **Technical relevance:** Separates BVH construction, traversal and scene-loading costs; offers deterministic small-scene intersection or Morton-sort correctness oracles, rather than assuming renderer frame-rate proves a kernel speedup.
- **Maturity/compatibility:** Work in progress; README requires Linux x86-64/glibc >=2.38, Pixi, raylib native shared library and supported GPU for accelerator tests. No build/test executed here. The [October 9 original grant-program article](https://www.modular.com/blog/nurturing-the-modular-ecosystem-the-modular-community-grant-program) describes the *planned* collision and batched physics roadmap, not evidence it has landed.
- **Potential replication:** CPU-only BVH ray-hit oracle against brute-force triangles, with degenerate/empty scenes and randomized seeds; GPU performance only after pinning hardware and driver.

### R02 — momanim: Mojo animation/video prototype (graphics and media)

- **Source/owner:** https://github.com/josiahls/momanim — Josiah Laivin; **lane:** newly examined repository; observed November 21.
- **Direct evidence:** Connected GitHub README inspected on `main`; describes an early/playground implementation of a 3Blue1Brown-style animation tool and provides `pixi run -e use-openh264 test_all`. The README explicitly warns that everything may break. No implementation, tests, or produced video independently inspected.
- **Technical relevance:** A useful non-LLM media pipeline target; distinguish rendering math, frame production and native OpenH264 codec overhead rather than attributing end-to-end time to Mojo.
- **Maturity/compatibility:** Experimental, toolchain version unverified; dependency and codec differences must be disclosed. The October 9 Modular article reports early image/video and shape APIs and a future 3D roadmap; do not promote roadmap to implemented features.
- **Potential replication:** Golden-frame pixel comparison for deterministic shapes, then separately profile render-only and encode-only throughput.
