## 2. Repository discoveries / deep dives — 12

### R01 — `DataBooth/mojo-toml`: native TOML parser/writer with explicit compatibility gates

**Repository:** https://github.com/DataBooth/mojo-toml  
**Domain:** parsing / serialization / configuration  
**Lane:** newly discovered existing project.  
**Evidence:** README and test/benchmark structure inspected.

The package implements TOML 1.0 parsing and writing in Mojo, reports 168 parser/writer tests, round-trip semantics, alternative numeric bases, nested tables and partial TOML 1.1 escapes. It explicitly keeps date/time values as ISO strings while Mojo's datetime surface is still moving, and documents `.mojopkg`/source-install tradeoffs.

**Why it matters technically:** it is a realistic grammar workload with tokenization, typed value construction, duplicate-key checks and serialization, not just a delimiter microkernel. The project also has a Python reference path and system-reporting benchmark scripts, which makes it suitable for correctness-first replication.

**Limitations:** README claims of full TOML 1.0 compliance and performance are project claims until the official TOML test corpus is independently run. Toolchain support is described broadly as Mojo 2025/2026 rather than a single exact compiler revision.

**Research angle:** run the official TOML conformance corpus first, then split lexer/tokenization from `TomlValue` materialization and writer cost.

### R02 — `Phelsong/mojo_csv`: multithreaded pure-Mojo CSV reader

**Repository:** https://github.com/Phelsong/mojo_csv  
**Domain:** parsing / concurrency / data processing  
**Lane:** newly discovered existing project.  
**Evidence:** README inspected.

`mojo_csv` reads a file into a raw string, exposes headers/elements and can partition work across logical cores; the README says it currently depends on MAX for parallelization. Writer and dict-reader paths are marked experimental, while SIMD within each thread, async chunking and streaming are roadmap items.

**Why it matters technically:** it gives a concrete contrast to `mojo-analyze` Category D: concurrency is used around a string-materializing parser rather than a single scanner hot loop.

**Limitations:** the published timings are author-reported and do not state a cross-language correctness oracle in the README. Large-file behavior still materializes the CSV and its elements.

**Research angle:** freeze an RFC-valid corpus, compare 1-thread versus N-thread parsing with a normalized row/field digest, and separate file read, split, unescape and string-allocation phases.

### R03 — `mzaks/mojo-csv`: RFC-4180 reader/writer with optional SIMD tokenization

**Repository:** https://github.com/mzaks/mojo-csv  
**Domain:** parsing / SIMD / serialization  
**Lane:** newly discovered existing project.  
**Evidence:** README inspected.

The library implements RFC-4180 reading and writing. Its reader can switch between scalar and SIMD tokenization; the author reports roughly 20% faster SIMD tokenization and gives M1 throughput expectations. The writer explicitly exposes the cost of escape detection and can skip it when the caller guarantees safe input.

**Why it matters technically:** scalar-vs-SIMD is already encoded as a controlled implementation choice, making this a stronger experiment candidate than copying an end-to-end throughput claim.

**Limitations:** performance numbers are author-reported on Apple M1 and are not `mojo-analyze` results. A parser benchmark must preserve quoted-field/newline correctness, not only bytes per second.

**Research angle:** reproduce the scalar/SIMD tokenizer delta on a fixed quoted CSV corpus and inspect generated vector code before comparing whole-table construction.

### R04 — `andresnowak/raylib-mojo`: manual Raylib bindings exposing incomplete-FFI constraints

**Repository:** https://github.com/andresnowak/raylib-mojo  
**Domain:** graphics / C FFI  
**Lane:** newly discovered technical backlog.  
**Evidence:** README inspected.

This is an intentionally incomplete Raylib binding with a small C/CMake bridge. The README warns that audio is not implemented, most functions are not tested, some struct mappings may be wrong, and historical Mojo FFI limitations complicate macOS and by-value C structs.

**Why it matters technically:** it is useful precisely because it shows where a graphics wrapper stops being “just bindings”: ABI layout and by-value structs become correctness constraints before frame-rate questions are meaningful.

**Maturity:** prototype/incomplete; compatibility notes may predate Mojo 1.x and must be revalidated.

**Research angle:** choose one POD struct and one function call, verify size/offset/value round-trip against a C oracle, then measure the call boundary separately from Raylib work.

### R05 — `msteele/mojo-sdl`: minimal SDL2 native binding

**Repository:** https://github.com/msteele/mojo-sdl  
**Domain:** graphics / systems FFI  
**Lane:** newly discovered technical backlog.  
**Evidence:** README inspected.

A deliberately small SDL2 binding runs without Python at runtime and includes a Mandelbrot presentation demo. Its narrow surface makes it easier to study the ABI boundary than a full game engine.

**Why it matters technically:** a minimal wrapper can serve as an FFI “null workload” for separating window/event-call overhead from rendering or fractal compute.

**Limitations:** very small project, no broad conformance or portability matrix documented.

**Research angle:** validate event/struct layout and a no-op renderer call against C before measuring presentation overhead.

### R06 — `RyanLeber/fire-physics-engine`: 2D physics demo whose limiting boundary is graphics FFI

**Repository:** https://github.com/RyanLeber/fire-physics-engine  
**Domain:** physics / simulation / graphics integration  
**Lane:** newly discovered technical backlog.  
**Evidence:** README inspected.

The engine is based on Box2D-lite ideas and is explicitly a Mojo capability demo. The author identifies Raylib FFI—not the solver itself—as the largest practical constraint and uses a compatibility binding layer. The roadmap includes replacing broad-phase collision detection and expanding shape support.

**Why it matters technically:** it offers a non-LLM workload where simulation correctness can be isolated from display/FFI, and where broad-phase algorithm choice may dominate once ABI friction is removed.

**Maturity:** demo; nightly-era requirements are historical and need current-toolchain verification.

**Research angle:** headless deterministic physics step with state digest, then measure solver and broad-phase separately from rendering.

### R07 — `gabrieldemarmiesse/mojo-zipfile`: Mojo-native ZIP/Deflate integration

**Repository:** https://github.com/gabrieldemarmiesse/mojo-zipfile  
**Domain:** compression / storage / compatibility  
**Lane:** newly discovered existing project.  
**Evidence:** README inspected.

The package mirrors common Python `zipfile` APIs, supports stored/deflated entries, streaming read/write, ZIP64 and CRC32 verification, and depends on the author's `mojo-zlib`. The README explicitly says compatibility/correctness currently outrank performance.

**Why it matters technically:** ZIP naturally decomposes into container parsing, checksum, compression library work and filesystem I/O, so it is a good example of a benchmark where total runtime must not be mislabeled as language compute.

**Research angle:** fixed archive fixture + Python/C oracle; validate central-directory metadata and CRC first, then isolate stored-entry overhead from Deflate cost.

### R08 — `DataBooth/mojo-dotenv`: modern `.env` compatibility rewrite

**Repository:** https://github.com/DataBooth/mojo-dotenv  
**Domain:** parsing / configuration / compatibility testing  
**Lane:** newly discovered existing project.  
**Evidence:** README inspected.

The project is a modern rewrite inspired by an older Mojo package and targets python-dotenv behavior: quoting, escapes, variable expansion, multiline values, `export`, parent-directory search and safe dictionary access. The README reports 49 tests and 98%+ compatibility and warns that compiled `.mojopkg` artifacts are Mojo-version-specific.

**Why it matters technically:** this is a compact compatibility workload where semantics are more important than speed and where an external implementation can act as a fixture oracle.

**Limitations:** the “production-ready” and compatibility percentages are author claims until independently exercised against the same test vectors.

**Research angle:** build a differential corpus against python-dotenv and classify semantic mismatches before any parser timing.

### R09 — `dorjeduck/kamo`: Kolmogorov–Arnold networks as a transparent Mojo learning implementation

**Repository:** https://github.com/dorjeduck/kamo  
**Domain:** numerical/scientific ML  
**Lane:** newly discovered older project, updated for Mojo 1.0 on 2026-08-22.  
**Evidence:** README inspected.

`kamo` ports a readable KAN implementation and supports B-spline+SiLU, Chebyshev and Gaussian-RBF edge functions plus MLP comparison. The author explicitly prioritizes transparency over speed and documents current type-system constraints around heterogeneous collections.

**Why it matters technically:** it is useful as a numerical correctness workload rather than a leaderboard: basis/derivative functions have direct mathematical oracles and can be benchmarked independently of training loops.

**Research angle:** finite-difference derivative oracle and one fixed basis-evaluation microkernel before any whole-training comparison.

### R10 — `randyzwitch/dataviz_mojo`: grammar-of-graphics chart builder

**Repository:** https://github.com/randyzwitch/dataviz_mojo  
**Domain:** visualization / developer tooling  
**Lane:** newly discovered current project.  
**Evidence:** README and documentation structure inspected.

The project provides a fluent plot builder, scales, themes, facets and multi-series layers with raster and SVG output. It depends on `canvas_mojo`, has release tags, API docs, generated examples and a benchmark task with a suspect-scaling gate. The README also explicitly warns that pre-1.0 API changes may be breaking.

**Why it matters technically:** plot construction and rendering can be separated: data transforms/scales, scene construction and backend rendering are distinct cost centers.

**Research angle:** deterministic scene specification with SVG/image digest; measure scene-build time separately from backend rasterization.

### R11 — `randyzwitch/canvas_mojo`: pure-Mojo raster/vector/PDF drawing engine

**Repository:** https://github.com/randyzwitch/canvas_mojo  
**Domain:** graphics / rasterization / image I/O / typography  
**Lane:** newly discovered current project.  
**Evidence:** README inspected.

`canvas_mojo` is unusually broad: native shape/path rasterization, gradients, compositing, font discovery/parsing, glyph rasterization, PNG/BMP/JPEG I/O, SVG/PDF backends, batch rendering and supersampling. The project reports byte-deterministic raster outputs, golden-image checks and a three-platform CI matrix on Mojo 1.1+.

**Why it matters technically:** it offers many non-AI, non-networking kernels with strong correctness hooks. It also documents a useful rule: parallel thresholds are measured rather than assumed.

**Limitations:** release benchmark numbers remain project measurements until reproduced; vector backends have viewer-dependent behavior and GPU acceleration is intentionally absent.

**Research angle:** pick one deterministic primitive (for example anti-aliased circles), preserve golden-image bytes, sweep batch size and inspect the parallel crossover.

### R12 — `ricardofitas/AoC-2025`: Rust/Qiskit/Mojo puzzle corpus

**Repository:** https://github.com/ricardofitas/AoC-2025  
**Domain:** mixed-language education / algorithms  
**Lane:** newly discovered technical backlog.  
**Evidence:** README inspected.

This repository solves selected Advent of Code 2025 problems in Rust, Python/Qiskit and Mojo, with Mojo intentionally kept near the Python-compatible subset for stability and run under WSL. It is not designed as a rigorous language benchmark, but it contains repeated algorithmic tasks across languages.

**Why it matters technically:** puzzle corpora can expose language/tooling ergonomics and algorithmic codegen across varied control-flow patterns, but only after implementations are normalized.

**Limitations:** personal AoC inputs are intentionally absent and existing timing summaries may mix algorithm/implementation differences. Qiskit variants are pedagogical, not performance peers.

**Research angle:** select one puzzle with generated public fixture, normalize the algorithm and answer checksum across Mojo/Rust/C before timing.

## 4. Deep-dive picks

1. **`mzaks/mojo-csv` scalar vs SIMD tokenization** — already exposes a narrow mechanism toggle and an RFC-based correctness target; a strong candidate for an independent codegen/performance replication.
2. **`canvas_mojo` deterministic primitive rendering** — unusually rich non-AI workload with byte/golden-image correctness and a documented multicore crossover policy.

4. **`mojo-zipfile` stored-vs-deflated split** — ideal for demonstrating why container parsing, CRC, compression-library work and I/O need separate timing contracts.
5. **`kamo` basis/derivative oracle** — small scientific kernel where numerical correctness can be independently verified before measuring codegen.

## 5. Ranked research candidates

1. **Category-D arm64 Span-mode CPU-time diagnostic (canonical unresolved hypothesis).** The Sep-23 affinity probe ruled out simple logical-CPU migration as a sufficient cause. Next, measure per-child process CPU time alongside the binary's existing wall time for the exact same checked-Span/pointer/C controls. If slow-mode wall time grows while child CPU time stays near the fast mode, host descheduling is implicated; if CPU time grows too, the cause lies in executed CPU/runtime/memory behavior. This outranks ecosystem candidates because it is an unresolved canonical thread.
2. **`mzaks/mojo-csv` scalar-vs-SIMD tokenizer replication.** Freeze a quoted RFC-4180 corpus, checksum token boundaries/values, then inspect vectorized assembly.
3. **`canvas_mojo` anti-aliased bulk-marker crossover.** Use a golden image/digest and sweep marker count with 1-thread versus package-selected parallel execution.
4. **`mojo-toml` lexer/materialization cut.** First run a conformance corpus; then use same-input semantic digest to time lexer-only versus typed-value construction.
5. **`mojo-zipfile` stored-entry boundary.** Measure ZIP container/CRC overhead without Deflate before adding compression-library cost.
