### O02. Pattern matching reaches end-to-end stdlib support through `hlcf.match`

**Freshness:** recent compiler/language development, 2026-09-14.  
**Sources:**
- https://github.com/modular/modular/commit/d71101f1ebb30404a3f78b18b87b96ae78fd165f
- https://github.com/modular/modular/commit/2f9e128f0614a31305838cb71c1785133a708f40

`__match` was reimplemented on `hlcf.match` to fix `or`-pattern and pattern-initialization issues, then wired through standard-library/e2e support. The author describes the implementation as reaching the shape needed for feature completeness and explicitly asks for nightly bug reports.

**Why it matters:** this is more than parser syntax. A new canonical high-level control-flow representation can affect initialization/lifetime handling and downstream optimization. It is still nightly work, so production code should not assume final surface syntax or semantics.

**Experiment angle:** once stable enough, compare equivalent branch trees versus match lowering with correctness fixtures first and generated control-flow/assembly second; do not infer a performance win from the language feature alone.

### O04. Portable latent sparse attention over window + compressed paged leaves

**Freshness:** recent MAX/GPU kernel change, 2026-09-14.  
**Source:** https://github.com/modular/modular/commit/ac7da051d96081a4784b87c1c4650e639bad9a2e

A new fused latent sparse-attention path walks a recent-window paged cache and a compressed-entry paged cache directly, performs online softmax including an attention sink, and exposes both Mojo and MAX kernel interfaces. The commit includes a scalar CPU path as reference and describes the portable GPU implementation as one block per query row/head group without tensor cores.

**Why it matters:** logical token indexing, compressed-entry indexing and physical cache paging coexist in the same kernel. It is a good example of why cache/layout benchmarks must specify indexing units and reference semantics, not only throughput.

**Experiment angle:** for a smaller future sparse workload, vary window/compressed-entry mix while holding output tolerance and cache residency constant; separate algorithmic sparsity benefit from paging/launch overhead.

## B. Repository discoveries — 12

### R01. `automata/modex` — Mojo coding-agent harness with reusable native HTTP/SSE/JSON layers

**Domain:** systems / networking / developer tooling.  
**Freshness:** newly discovered current WIP.  
**Repository:** https://github.com/automata/modex

The project is an intentionally unstable Mojo coding-agent harness. Its reusable `libs/` include a libc/OpenSSL HTTP client, chunked decoding, SSE parsing, a native JSON parser/serializer, LLM-provider clients and built-in tool dispatch. The app layer remains separate from reusable packages.

**Why interesting:** the technically useful part is not “agent” branding but a real native networking + streaming + parsing stack in Mojo. Its WIP status means APIs and current nightly compatibility can move quickly.

**Research angle:** isolate incremental SSE parsing or chunked-transfer decoding with exact byte fixtures before attempting end-to-end agent latency.

### R02. `murtazox04/mojogram` — Telegram bot framework built around Mojo-native foundations

**Domain:** web/runtime/concurrency.  
**Freshness:** newly discovered current project; evidence inspected through the author's project summary.  
**Repository:** https://github.com/murtazox04/mojogram

The author describes a pure-Mojo Telegram framework with a hand-written JSON arena DOM, system-curl transport, `parallelize` batch execution, atomic state protection and a libc-socket webhook server. The published throughput/latency numbers are **author-reported**, not reproduced here.

**Research angle:** extract one deterministic JSON update parse or concurrent state primitive; validate semantics first and keep subprocess/network latency outside the language-kernel measurement.

### R03. `lee101/mojojojo-agent` — mixed Python/Mojo agent with explicit native hot paths and benchmarks

### R05. `HJLebbink/sort-networks-mojo` — branch-free sorting networks for small fixed-size inputs

**Freshness:** newly discovered technical backlog; README examples target **Mojo 0.7-era** compiler behavior.  
**Repository:** https://github.com/HJLebbink/sort-networks-mojo

The project implements sorting networks for small inputs and documents AVX-512-oriented generated assembly. Its README is refreshingly skeptical about benchmark quality and notes floating-point NaN handling that adds instructions in generated code.

**Research angle:** port one 8/16-element integer network to Mojo 1.x, verify exact sorted outputs over adversarial inputs, then compare code shape and repeated-latency against stdlib sort. Do not reuse the old timing numbers as current evidence.

## D. Deep-dive picks

1. **Pattern matching compiler path:** `__match` now has end-to-end support via `hlcf.match`; interesting for semantic/control-flow correctness before performance.
2. **Variable-length loop transformations:** yesterday's fixed-width FNV result showed manual unrolling can close a codegen gap. The real Category D hash loop has dynamic key lengths, making it the right place to test whether that lesson survives a production-like workload.
3. **Sorting networks:** an old but clean branch-free workload that could become a modern small-array codegen benchmark after a Mojo 1.x port.
4. **Native streaming stacks:** modex and mojogram expose JSON/SSE/HTTP primitives that can be measured independently of LLM/API/network latency.
5. **GPU benchmark attribution:** latent sparse attention, robotics and RDNA3 GEMM all reinforce that layout, transfer, power/clock state and reference semantics are first-class variables.

## E. Research candidates

Ranked for `mojo-analyze`:

1. **Real Category-D variable-length FNV unroll probe** — keep the existing CSV parser, `List` slots, probing/equality/aggregation and checksum unchanged; replace only the byte-at-a-time FNV loop with a 4-byte manually unrolled loop plus tail, run 2 warmups + 7 trials on Linux x86_64/arm64, and inspect assembly. This directly tests whether the fixed-width unrolling lesson generalizes.
2. **Small sorting-network modernization** — port 8/16-element integer network to Mojo 1.x, exact sorted-output oracle, then inspect branch-free SIMD codegen against stdlib sort.
3. **SSE/chunked parser primitive** — extract one deterministic streaming decoder from a current native Mojo stack and compare fragmented-input correctness plus throughput.
4. **RESP codec conformance micro-workload** — revive only a small Redis protocol encoder/decoder on current Mojo; byte-exact oracle before any server benchmark.
5. **GPU power/transfer provenance fixture** — add a reusable metadata checklist for device clocks/power profile, driver/runtime and host↔device transfer scope before future accelerator experiments.
