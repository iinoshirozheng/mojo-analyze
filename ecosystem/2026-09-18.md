## 1. Important current developments — 4

### O01 — Mojo 1.1.0 ships with compiler/code-size and collection-growth improvements

**Lane:** recent development — 2026-09-17.  
**Source:** https://mojolang.org/releases/v1.1.0/

Mojo 1.1.0 adds contextual leading-dot member references such as `.float64`, continues the migration to unified closures, broadens stable standard-library APIs, and removes additional pre-1.0 syntax. The release notes also document concrete implementation improvements: `List.extend`/`resize` now grow geometrically instead of quadratically, t-string compile-time encoding is reported roughly 7× faster for that step, and a 2,500-distinct-t-string stress case drops emitted helper functions from 2,510 to 14 with an approximately 85% smaller object.

**Why it matters technically:** the release contains both source-language changes and optimizer/library effects. Existing benchmarks pinned to Mojo 1.0 should not silently absorb 1.1 behavior, but these changes create good stable-vs-stable differential candidates.

**Research angle:** isolate one affected mechanism—large `List` growth or t-string-heavy compile workload—while pinning source, compiler revisions, cache state, and correctness separately from runtime benchmarking.

### O02 — Modular 26.6 opens the compiler to external contributions

**Lane:** recent development — 2026-09-17.  
**Source:** https://www.modular.com/blog/modular-26-6-open-compiler-contributions-audio-generation-and-expanded-model-support

Modular 26.6 is the first platform release after the Mojo compiler was open-sourced in August. Mojo 1.1 now accepts external compiler contributions, while MAX 26.6 adds audio-generation support and additional model/hardware work.

**Why it matters technically:** compiler implementation details are now not only inspectable but contribution-addressable. For `mojo-analyze`, unexplained codegen gaps can increasingly be reduced to reproducible compiler-level cases instead of remaining black-box observations.

**Research angle:** when a codegen delta survives a minimal reproducer, record the exact KGEN/MLIR stage and source SHA so the experiment can become an upstream-quality compiler case rather than only a benchmark note.

### O03 — declared MAX custom ops gain a cached, rank-polymorphic interpreter path

**Lane:** recent development — landed 2026-09-17.  
**Sources:**  
- declaration API: https://github.com/modular/modular/commit/c4c526a3999cf2c5f2bedd03ec5da5ba01e63b8d  
- cached interpreter binding: https://github.com/modular/modular/commit/136690e83ebff9139bccf5908d3656523404d0db

`max.experimental.custom.declare` lets a custom op declare input/output signatures once and compile its Mojo source package at declaration time. A paired change routes representable declared ops through a cached interpreter binding keyed by dtype and rank rather than exact shape, so shape-only changes do not force recompilation; unsupported cases fall back to graph compilation.

**Why it matters technically:** this separates declaration/compile cost from shape-varying execution and makes cache-key design a first-class performance variable.

**Research angle:** a fair compile-vs-execute benchmark should vary shape while holding rank/dtype constant, then cross rank/dtype boundaries deliberately and count compilations as well as wall time.

### O04 — MAX fixes hidden per-step GPU transfer in ModuleV3 rotary embeddings

**Lane:** recent development — landed 2026-09-17.  
**Source:** https://github.com/modular/modular/commit/bde9049aeeab49488deabc83ce89167735660d4f

A precomputed rotary-embedding frequency table had been created on GPU 0. In multi-device models that made later distribution a GPU-to-GPU transfer that was not hoisted into initialization and therefore could run on every `execute` step. The fix creates the constant on CPU so normal initialization transfer machinery can place it on each target device; the commit reports that this closes the ModuleV2/ModuleV3 performance difference for the affected path.

**Why it matters technically:** a nominally constant tensor can become recurring runtime data movement if its ownership/device placement is wrong. Kernel timing alone would miss the source of the regression.

**Research angle:** include transfer counts and initialization/execution phase boundaries whenever comparing graph/model authoring paths.

## 2. Repository discoveries / deep dives — 12

### R01 — `conorbronsdon/mojo-xml`: ElementTree-shaped XML with differential fixtures

**Repository:** https://github.com/conorbronsdon/mojo-xml  
**Domain:** parsing / serialization / Unicode  
**Lane:** newly discovered existing project.  
**Evidence:** README/test design inspected; performance not reproduced.

Pure-Mojo XML parsing builds a scoped-namespace DOM around a pull parser, including Clark-notation namespace resolution, text/tail semantics, encoding normalization, serialization, and a pragmatic ElementTree query subset. The project reports 14/14 canonical-tree byte matches against CPython fixtures, 159 unit/error/pull-parser tests, and a 6,000-iteration fuzz drive.

**Why it matters:** it is a strong example of compatibility-first benchmarking: define a semantic oracle before measuring parser throughput.

**Experiment angle:** use one bounded XML corpus and compare tokenizer-only versus DOM-building stages, gated by the same canonical tree digest.

### R02 — `conorbronsdon/mojo-markdown`: CommonMark parser with explicit divergence accounting

**Repository:** https://github.com/conorbronsdon/mojo-markdown  
**Domain:** parsing / text processing  
**Lane:** newly discovered existing project.  
**Evidence:** README/conformance model inspected; published conformance is author-reported.

The parser uses a byte-level block/inline pipeline, a delimiter stack for emphasis, an arena-backed block tree, and bounded container nesting. Its conformance scoreboard reports 643/652 CommonMark examples (98.6%), with all nine failures documented rather than hidden; the project also fuzzes adversarial nesting and delimiter runs.

**Why it matters:** benchmark correctness can be expressed as a known-divergence set, not merely a single checksum. This is useful for parser workloads where several implementations may intentionally support different language subsets.

**Experiment angle:** a Mojo-vs-reference rendering benchmark should pin the accepted CommonMark subset and fail if the divergence set changes unexpectedly.

### R03 — `visorcraft/MongrelDB-Mojo`: Mojo database client whose hot boundary is Python interop

**Repository:** https://github.com/visorcraft/MongrelDB-Mojo  
**Domain:** database / Arrow / HTTP / Python interoperability  
**Lane:** newly discovered existing project.  
**Evidence:** README/API inspected; current README still targets Mojo 0.25.7.

The client exposes CRUD, SQL, Arrow IPC, vector/full-text query features, transactions, auth and maintenance operations, but transport/JSON/base64 use Python standard-library modules via `Python.import_module`. It explicitly has no third-party package or C-FFI requirement, yet it is not a native Mojo networking stack.

**Why it matters:** “written in Mojo” does not imply that network and serialization costs run in compiled Mojo. Interop ownership and conversion boundaries need separate attribution.

**Experiment angle:** benchmark request construction/response flattening independently from Python `urllib` transport; do not label server RTT as Mojo client throughput.

### R04 — `BradLarson/max-cv`: fused image-processing graphs on MAX

**Repository:** https://github.com/BradLarson/max-cv  
**Domain:** image/video processing / MAX graph / GPU  
**Lane:** newly discovered existing project.  
**Evidence:** README architecture inspected; toolchain requirement is MAX 25.4+ with nightly preferred.

MAX-CV defines platform-independent image operations in Mojo, constructs them as MAX graphs, compiles once, and reuses the compiled graph against many images; outputs can stay resident on an accelerator for downstream pipelines.

**Why it matters:** it cleanly exposes compile-once versus steady-state execution and offers an application domain where fusion can change memory traffic more than individual operator arithmetic.

**Experiment angle:** compare one operator chain as separate materialized stages versus a fused graph, reporting compilation, host/device transfer and steady-state execution separately.

### R05 — `lee101/mojo-numpy`: compiled Mojo numeric loops behind a NumPy-shaped Python package

**Repository:** https://github.com/lee101/mojo-numpy  
**Domain:** numerical computing / Python ABI / CPU+GPU  
**Lane:** newly discovered existing project.  
**Evidence:** README implementation and benchmark methodology inspected; numbers are author-reported.

The package keeps arrays owned by Python/NumPy and sends contiguous buffer addresses through a C ABI into one compiled Mojo shared library. It covers ufuncs, reductions, sorting, selected linear algebra and random generation; CPU matmul can use OpenBLAS, while an explicit GPU path uses a Mojo kernel. The README usefully discloses mixed outcomes—some loops ahead of NumPy, sorting/matmul behind, and platform/library-sensitive linear-solve results.

**Why it matters:** it demonstrates why language benchmarking must disclose linked libraries and ownership/copy policy. A Mojo wrapper around OpenBLAS is not a pure Mojo matmul comparison.

**Experiment angle:** isolate one self-contained reduction or RNG kernel with no BLAS and report Python↔Mojo call overhead separately from bulk compute.

### R06 — `Hammad-hab/CombustUI`: low-level Mojo GUI over FLTK C++

**Repository:** https://github.com/Hammad-hab/CombustUI  
**Domain:** GUI / FFI / event runtime  
**Lane:** newly discovered existing prototype.  
**Evidence:** README inspected; API described as functional but still evolving.

CombustUI wraps FLTK through low-level bindings and provides basic events, windows, inputs, buttons, scrolling and layout. The repository also contains compiler time-trace artifacts, making build-time/FFI investigation more interesting than frame-rate claims at this maturity level.

**Why it matters:** UI benchmarks should separate widget/layout command construction, FFI dispatch and native toolkit rendering/event-loop costs.

**Experiment angle:** measure a deterministic layout/update command batch without display/vsync and compare direct FFI-call count with batched command submission.

### R07 — `ehsanmok/json`: spec-gated SIMD/tape JSON with CPU and GPU backends

**Repository:** https://github.com/ehsanmok/json  
**Domain:** JSON / SIMD / GPU / reflection  
**Lane:** newly discovered existing project.  
**Evidence:** README, conformance and benchmark descriptions inspected; throughput figures are author-reported.

The default CPU path is described as a two-pass pure-Mojo parser with a 64-byte branchless structural scan and packed tape. CPU/GPU backends share the tape representation; the project also implements reflection serde, JSONPath/Pointer/Patch/Schema and keeps conformance catalogs as CI gates with declared expected failures. GPU support is opt-in because it adds MAX licensing/runtime dependencies.

**Why it matters:** this directly complements `mojo-analyze` Category E: structural indexing, tape construction, materialization and schema/serde are distinct stages, and author benchmarks already distinguish parse-only from parse+traverse.

**Experiment angle:** replicate only a structural-index checksum on the existing deterministic Category-E corpus before considering end-to-end parser comparisons.

### R08 — `gabrieldemarmiesse/mojo-zipfile`: ZIP container logic over zlib

**Repository:** https://github.com/gabrieldemarmiesse/mojo-zipfile  
**Domain:** compression / file formats / CRC  
**Lane:** newly discovered existing project.  
**Evidence:** README/API inspected.

The project mirrors Python `zipfile` concepts and supports stored/deflated entries, streaming reads/writes, ZIP64 and CRC32 verification. Compression itself depends on `mojo-zlib`, so container parsing, CRC and zlib codec cost should not be conflated.

**Why it matters:** ZIP offers several deterministic boundaries—central-directory parsing, CRC32, compression/decompression and I/O—that can be benchmarked independently.

**Experiment angle:** use fixed archives and a byte-exact extraction digest; measure CRC separately from DEFLATE and container traversal.

### R09 — `nabla-ml/nabla`: scientific ML and autodiff on Mojo/MAX

**Repository:** https://github.com/nabla-ml/nabla  
**Domain:** scientific ML / autodiff / distributed execution  
**Lane:** newly discovered existing project.  
**Evidence:** public project docs inspected; main requires Modular nightly.

Nabla combines imperative and functional APIs, allows custom Mojo kernels inside its autodiff engine, and describes distributed SPMD sharding plus a lazy MAX-native execution model.

**Why it matters:** it is a useful source for experiments where kernel arithmetic, autodiff graph overhead and distributed/sharding costs can be separated instead of comparing whole training loops.

**Experiment angle:** choose one differentiable primitive with a NumPy/JAX numerical oracle and validate forward + gradient before timing eager/lazy/custom-kernel variants.

### R10 — `konjoai/vectro`: embedding quantization with mixed Mojo/Rust/Python paths

**Repository:** https://github.com/konjoai/vectro  
**Domain:** vector compression / SIMD / ANN  
**Lane:** newly discovered existing project.  
**Evidence:** README/release documentation inspected; performance figures are author-reported and include multiple backends.

Vectro covers INT8/NF4/PQ/binary quantization, HNSW and storage/integration layers. Its README explicitly distinguishes Python fallback, Rust extension and optional compiled Mojo paths and includes reproducibility controls such as revision/SIMD/thermal/thread metadata and a coefficient-of-variation gate.

**Why it matters:** it is technically interesting less for headline “vectors/s” than for its multi-backend benchmark design and compression-quality contracts.

**Experiment angle:** reproduce one fixed-dimension INT8 quantization kernel with an exact/quality oracle and identical normalized-input assumptions across Mojo and one native comparator.

### R11 — `msteele/mojo-sdl`: minimal direct SDL2 binding

**Repository:** https://github.com/msteele/mojo-sdl  
**Domain:** graphics / native FFI  
**Lane:** technical backlog / newly surfaced older prototype.  
**Evidence:** README/source layout inspected; very small project.

This is a deliberately minimal native SDL2 binding with no Python at runtime and a Mandelbrot demo. Its tiny surface makes it more useful as an ABI/FFI learning artifact than as a general graphics framework.

**Why it matters:** a small binding lets ABI shape, symbol loading and call overhead be checked without a large engine obscuring the boundary.

**Experiment angle:** validate a handful of SDL struct/constants/function calls against a C oracle before attempting event or rendering throughput measurements.

### R12 — `fnands/mimage`: early pure-Mojo image-format experiment with an explicit zlib boundary

**Repository:** https://github.com/fnands/mimage  
**Domain:** image decoding / compression boundary  
**Lane:** technical backlog / newly surfaced older prototype.  
**Evidence:** README and open compression issue inspected; project is early and not fully pure Mojo.

Mimage aims for Pillow-like image I/O but currently documents basic 8-bit PNG reading and an unresolved C zlib `uncompress` dependency. The project itself marks the “pure Mojo” status with an asterisk and tracks replacing the codec boundary separately.

**Why it matters:** this is exactly the kind of maturity/evidence distinction the radar should preserve: PNG parsing can be Mojo while DEFLATE remains external.

**Experiment angle:** if revived on Mojo 1.x, first build a PNG conformance/checksum fixture; only then separate chunk/filter logic from zlib decompression.

### A06 — Deep dive into ownership in Mojo

## 4. Deep-dive picks

1. **Mojo 1.1 compile/runtime differentials:** `List` growth and t-string changes are compact, measurable stable-vs-stable experiments, but they should not mutate the 1.0 canonical benchmark lane by default.
2. **`ehsanmok/json`:** its structural-index → tape → traversal decomposition is the closest external design analogue to Category E and offers a concrete route away from monolithic parser timing.
3. **`mojo-numpy`:** the project is valuable for methodology because it explicitly exposes C ABI ownership, OpenBLAS use, GPU fallback and mixed results rather than treating all work as one Mojo kernel.
4. **MAX custom-op caching:** rank/dtype cache keys versus shape changes offer a clean compile-frequency experiment that reports both compilation events and execution time.
5. **XML/Markdown conformance projects:** both demonstrate stronger correctness contracts than a single aggregate checksum and are good templates for future parser workloads.

## 5. Research candidates

Ranked candidates after comparing today's discoveries with unresolved repository hypotheses:

1. **Category D file-ingestion vs in-memory scanner boundary** — strongest canonical continuation. Run the exact same scanner after preloading bytes outside the timer and compare with end-to-end read+scan in the same binary/workflow; preserve checksum identity on x86_64 and arm64. This directly follows the Sep-17 result that the gap already exists before numeric parsing.
2. **Mojo 1.0 vs 1.1 `List` growth differential** — grow to several controlled sizes, verify final contents/capacity semantics, measure runtime/allocation behavior and inspect whether the new geometric growth removes the documented quadratic path.
3. **JSON structural-index micro-contract** — derive a deterministic structural-position checksum from Category E and compare its scalar/SIMD lowering independently of materialization.
4. **Declared custom-op cache-key probe** — vary shape under fixed rank/dtype, then cross rank/dtype to verify compile-count behavior documented by MAX.
5. **FFI ABI oracle** — use the tiny SDL binding or one MAX-CV-style C boundary to verify struct size/alignment/value passing before any call-overhead benchmark.

**Selected for Phase 2:** candidate 1, because it is the next unresolved semantic boundary already justified by the repository's latest verified research rather than a new ecosystem-only hypothesis.
